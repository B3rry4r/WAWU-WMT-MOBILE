# FIX-27 · The schools list pages the same way on every database, so no school is skipped

## Read first

- `docs/WORKFLOW.md`, `docs/roles/BUILDER.md` or `docs/roles/VERIFIER.md`
- `tasks/SCHOOLS-04.md` (its D2: a cursor for every name the admin accepts) and the backend's `src/schools/` cursor code
- The backend's `.github/workflows/deploy.yml` (the Test job runs the full jest suite on a `postgres:16` container before every deploy)

## Goal

Backend main dc3baa2 (the SCHOOLS-04 merge, 8 Oct 2026 22:09 UTC) failed its pre-deploy Test job, so production was not updated and stays on d92e998. One suite failed, `src/schools/tests/schools-admin-written.contract.spec.ts`, 2 tests (5719 others passed):
- "a walk at limit 1 passes both longest names and reaches the school after each": the longest name came after its neighbour (`indexOf` 1, expected before).
- "the name in a cursor may be as long as the admin allows, and no longer": the page after the cursor held no school where `units-next` was expected.

Both pass on the build machine. The likely cause is collation: CI's `postgres:16` image sorts text by `en_US.utf8`, the build machine's databases do not, and the cursor's comparison and the list's order disagree under one of them. If production's database sorts like CI's, a person paging the schools directory can miss schools. Find the real cause first; do not assume this one.

## Scope

- Reproduce the failure locally on a database that sorts as CI's does (a database created with the CI image's locale, or an ICU collation that gives the same order; say which and show it fails on main dc3baa2 before any change).
- Fix the code so the order and the cursor agree on every collation (for example one explicit collation for both the `ORDER BY` and the cursor comparison), not by changing the test's expectations. The order people see must stay sensible (state what changes, if anything, for ordinary names).
- Find any other cursor-paged list ordered by text with the same weakness (`grep` the backend for cursor code ordered by a name or title); fix them the same way or list each in the report with why it is safe.
- The full jest suite and the protected suite pass on both kinds of database.

## Capability checks

- [ ] The two failing tests pass on that database and on the build machine's, unchanged in what they assert.

**Cause (not the one the task guessed).** The list and its cursor did NOT disagree on the CI database. Both ran on the column's own collation, and a walk at every page size on unchanged dc3baa2 visits each school once, in the order of one big page, on the glibc database (the final spec's walk test, which at limit 1 is a cursor at every one of the 42 schools, and its hidden-school test pass on dc3baa2 there: `before-final-spec-ci.log`). The two tests failed because they assume where one pair of characters sorts: a Han character outside the BMP (U+20000) after the white flag emoji (U+1F3F3 U+FE0F), which the fixture's own comment says holds "in byte order and in ICU's". glibc's `en_US` puts them the other way round (checked: glibc U+20000 < flag < a; ICU flag < a < U+20000; C a < flag < U+20000), so on CI the neighbour name (the same text with the Han character last) lists BEFORE the longest name, the walk never meets the order the test was written for, and the page asked for after the longest name's cursor is empty. The real defect underneath is the one the task named in general: the order a person sees was whatever the database's collation made it, so it differed between CI, a laptop and an ICU database, and nothing in the code or a spec pinned it.

**Fix.** The order is written into the query, in one place. `src/schools/schools-order.ts` builds three expressions, used for BOTH the `ORDER BY` and the cursor's row comparison: `lower(name COLLATE "C")`, then `name COLLATE "C"`, then `id COLLATE "C"`. `"C"` is built into every Postgres (no ICU or locale package needed) and `lower()` under `"C"` lowers ASCII only, the same on every database (checked on all three: `lower('ÉCOLE Ǆ İ ABC' collate "C")` gives `École Ǆ İ abc` everywhere, where the plain `lower()` differs between them). `GET /schools` now reads the page's ids and names with one `$queryRaw` (the filter written as SQL: not hidden, category, and the search as `ILIKE` on name, place or a shown course title with the same `\`, `%`, `_` escaping), then loads those rows with Prisma (`findMany` by id, `hiddenAt` null, courses as before) and puts them back in the query's order; the next cursor is taken from the query's last row, so a school hidden after it was read still marks where the next page starts. The cursor text (`["name","id"]`, base64url) and its bounds in `schools-cursor.ts` are unchanged, so no client and no cursor already in hand changes. The inbox keyset already pinned `COLLATE "C"` on both sides (INBOX-07); this is the same rule. `docs/contract/CONVENTIONS.md` section 6 gets one bullet that says it.

**What people see.** Against an `en_US` database (CI, and possibly production, see below): names in ordinary Title Case with single spaces keep their order, and lower-case first letters keep theirs. On a 45-name sample of plausible school names (`names.sql`, `q5.sql`), 951 of 990 name pairs (96%) keep the `en_US` relative order; plain `COLLATE "C"` would have kept 861 (87%) and sent "iLearn Academy", "eHealth Africa Institute", "uLesson Studio" and "altSchool Africa" to the end of the list, which is why the first step lowers ASCII capitals. Of the 39 pairs that flip, 23 are the one accented name; the other 16 are a hyphen, apostrophe, ampersand, "St." or a digit beside a space (listed in `q9.sql`). Examples, `en_US` then now: "Dee-Jay Music School" before "Dee Jay Studio" becomes "Dee Jay Studio" before "Dee-Jay Music School" (a space sorts before a hyphen); "D'Lite Beauty School" moves from between "Digital Dreams" and "Ecole" to before "Dee Jay" (an apostrophe sorts before letters); "Lagos-Island Academy" moves from beside "Lagos Island Academy" to after "Lagos Studios"; "École Hôtelière" moves from the E's to after "Zuri Training" (an accent is past Z). Against a `C.UTF-8` database (this machine, the default of a plain Ubuntu droplet): capitals-first order was case-sensitive, so every lower-case-first name moves up among its letter; names starting with a capital do not move. Accented first letters sort after Z in every case. Folding accents would need the `unaccent` extension or a translate table; left out (decision D3).

**Decisions (Default (agent), owner may override).**
- D1. `COLLATE "C"`, not an ICU collation (`und-x-icu`). Why: `"C"` exists on every Postgres; ICU collations exist only if the server was built with ICU and the collation was imported at `initdb`, and production's server is not written down. A missing collation would turn every `GET /schools` into a 500. The inbox already uses `"C"`.
- D2. ASCII capitals are lowered for the first sort step, so the list reads A to Z whatever the case of the first letter. Plain `"C"` was the simpler choice and would have buried "iLearn Academy" after "Zuri Training".
- D3. Accents are not folded: a name that starts with "É" sorts after Z. Rare for this directory; folding needs the `unaccent` extension or a translate list, and neither is guaranteed. A follow-up can add it in `schools-order.ts` only.
- D4. No migration and no new index. The `@@index([name])` is on the default collation and cannot serve this order; the directory is an admin-curated list (tens to hundreds of rows), so a scan and sort is cheaper than the index. If it ever grows to many thousands, add an expression index on `(lower(name COLLATE "C"), name COLLATE "C", id COLLATE "C")` in its own task.
- D5. Two reads (ids and names by SQL, rows by Prisma) rather than one wide raw query: the card builder and the course ordering stay exactly as SCHOOLS-04 left them. A school hidden between the two reads drops out of that page, which can make one page a school short; the cursor still comes from the first read, so nothing is skipped.
- D6. The two SCHOOLS-04 specs are untouched. The new spec states the promised order in plain code (no SQL, no database), so it gives one answer on any database.
- D7. The `GET /communities` tie-break gap is reported, not fixed here (it is not a collation weakness and has its own protected-route behaviour to check).

### Findings

**D1 (defect, spec gap, test-only): `schools-collation.contract.spec.ts` cannot tell `lower()` from `upper()` in the first sort key.** None of its names has `[`, `\`, `]`, `^`, `_` or a back-quote beside a letter, and the order it promises ("A to Z ignoring ASCII case") is the only thing that separates the two. Reproduce: in `src/schools/schools-order.ts` change both `lower(` to `upper(`; `npx jest --runInBand src/schools` on the glibc `en_US` database passes 43 of 43 (`mut/mutants.out`, M14). The product code is right as written. Fix: add two names to the spec's `AWKWARD` list, for example `"A_B School"` beside `"AB School"` and `"_Under First"`; its own `expectedOrder` already uses ASCII lower-casing, so the mutant then fails. No product change.

**N1 (unclear, for SCHOOLS-03 and the builder): the list is now two reads, so a school hidden between them shortens the page.** Reproduced with the built service and a hook between the two reads (`live/race.js`): hiding one of five schools between the reads gives a page of 4 with `nextCursor` set, hiding all five gives `items: []` with `nextCursor` set. Nothing is skipped (the walk onward saw each later school exactly once). Before, a page was one statement. Judgement: acceptable (the window is milliseconds, and it only ever shortens a page), but the directory screen (SCHOOLS-03, not built) must continue on `nextCursor`, never on "the page was full", and the builder's D5 should say so in SCHOOLS-03.

**N2 (owner note, not a defect): what people see.** On a 75-name sample of plausible Nigerian school names that I wrote (`people/names.txt`, result in `people/result.txt`), 2492 of 2775 name pairs (89.8%) keep the `en_US` relative order (plain `"C"` would keep 82.0%). Title Case names, `iLearn`, `altSchool`, `eHealth`, `uLesson` keep their place. What moves: a name starting with an accented letter goes after the Z's (`Èdè Yorùbá Institute`, `Ìrẹ̀tì Language Centre`, `École Française de Lagos`, `Ọ̀rẹ́ School of Arts`, `Åkesson Design School` go from the E, I, O and A groups to the end), and a space, hyphen or apostrophe now sorts before letters (`St Mary's Vocational Centre` before `Stanbic Business Hub`, `D'Banj Academy` first among the D's, `Lagos-Island Culinary Institute` after `Lagos Studios`). Not plainly wrong; Yoruba and French first letters are the likeliest to be noticed in a Nigerian directory, and a fold of the common Latin accents with `translate()` inside `schools-order.ts` alone (no extension, no migration) would remove it if the owner wants that.

**N3 (note): performance.** The existing `School_name_idx` cannot serve the new order. 20,000 rows in a scratch table: top-N heapsort over a sequential scan, 10 ms a page (4.6 ms with a cursor), against 0.07 ms by index before. The directory is tens to hundreds of rows, so the builder's D4 stands.

**N4 (note): other cursor-paged lists.** I read every non-test file that mentions a cursor: chat, paid DMs (thread aggregate keyed `(last_at, other)` with both sides in one statement), `/me/*`, money history, live catch-up, the admin school list (Prisma cursor on `createdAt, id`): all keyed on a time and an id; inbox pins `COLLATE "C"` on its text key on both sides. Creator discovery orders by `handle` but is offset-paged, and `GET /communities` orders by `name` alone with offset paging (no tie-break, as the builder said; a protected route, not changed here). The builder's "no other cursor-paged list has a human-text key" is right.

**N5 (note): doc wording.** The new CONVENTIONS bullet says a cursor compared against a list left to the column "can disagree with the page". For the schools list that did not happen (above); the sentence is true as a general rule for a comparison made in another collation than the `ORDER BY`. Fine as written.
