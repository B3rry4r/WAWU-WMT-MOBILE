**Why the list row did not show.** Two walk problems, both reproduced, neither a defect of this task. (1) `stack.sh` prints the app at `http://127.0.0.1:7903/`, but the Hub's CORS list holds `localhost` origins only, so a page opened at 127.0.0.1 blocks every Hub call and the list shows "Couldn't load your notifications. No connection." Opened at `http://localhost:7903/` the row is there, with the right words, the Messages icon and the dot. (2) The notice is written 5 to 10 s after the message, and the list loads once when it opens and does not refresh itself (`NotificationFeedScreen.tsx` has no polling, for any kind): a list opened before the sweep wrote the row keeps its old rows until it is reopened or refocused (open list stayed on the old row for 8 s while the API held the new one; a reload showed it).

**What passed live.** A and B (B the host) each had ONE row counting three after C posted three messages; C had none. Tapping the row opened `/community/<id>` and sent the notice read and the room read. With the room left, the next message made a NEW notice for A (1 message) while B's unread one grew to 5. A person still inside the room gets no notice (the room marks itself read as the message arrives). With A's Community messages switch off in the app, A got no new notice and B kept getting counted. A person who left got none. One push per notice, none while it grew, a new one after the room was opened, none with the switch off, and the payload opens the room (`actionHref`, `target`): shown with a throwaway spec against the real sender and the Expo stand-in, which was deleted (a copy is in the verifier folder, `live-push.spec.ts.txt`). 1204 recipients in one room: one notice each, 4 transactions (paging works past 500; `paging.spec.ts.txt`).

**Message posted then deleted before the sweep.** Not counted: the sweep reads the rows that exist, and there is no delete route for a community message in the Hub (rows go only with the room or the sender's account purge). A message already counted keeps its count when it is deleted later. That is right for this product.

### Open findings

- **high H1** `src/community-message/community-message-notice.service.ts:173-192` (claim) with `src/notification/notification.service.ts:495`: a window folded again counts its messages again. The second pass ends later (`to` is `now - settle`), so notices the first pass wrote (`countedUpTo` = the old end) are not skipped. A Hub that stops after writing and before `release`, a lease that expires (120 s, never renewed in a long pass) or any one room failing in the pass (the cursor is held and every room is folded again) double counts. Repro on the stack: C posts 2 messages (B's notice 8 to 10), set `CommunityNoticeCursor.countedUpTo` back to its earlier value, wait one pass: B's notice says 12 with 10 messages in the room. The 200-member spec cannot see it: its messages are in 2024, which pins `to` at the cursor plus 10 minutes both times. A room that fails every pass also holds the cursor for all rooms (nothing new is noticed anywhere once the 10 minute cap is reached). Fix: count only messages newer than the notice's own `countedUpTo` (`since = max(read mark, joined, notice.countedUpTo)`), keep failure to one room, renew or drop the lease, and add a spec whose second pass ends later.
- **low L1** `src/notification/notification.service.ts:487`: a muted person's unread notice is marked read on the next message in that room (the muted `continue` runs before `staleIds.delete`). Repro: A has an unread notice, turns the switch off, C posts: the notice flips to read and the dot goes. The gate comment says it "stays in the list".
- **low L2** stale words: `src/notification/tests/notification-switches.contract.spec.ts:389` title still says "no community message kind exists"; `prisma/schema.prisma:1807` comment on `NotificationSettings.communityMessages` still says "It gates nothing today: no community message kind or sender exists yet".
- **low L3** (test gap) the new push test (`community-message-notice.contract.spec.ts` last test) only runs `enqueue()`, never a send; the throwaway spec above (one buzz, none for growth, new after open, none with switch off, payload) would kill it.
- **low L4** `migration.sql` builds `CommunityMessage_sentAt_idx` without CONCURRENTLY, so message inserts wait while it builds; 20000 rows took under a tenth of a second, a large table would take longer.
- **low L5** the open notification list does not refresh itself (all kinds); a notice lands 5 to 10 s after the message. Existing behaviour, not for this task.
- **low L6** the sweep's only guard for a slow commit is the 5 s settle, and `sentAt` is the Hub's clock while the cursor is the database's.
