## Builder report

Files (Hub): new `src/legal-intake/ai/elevenlabs-legal-ai.ts` (the adapter), `src/legal-intake/ai/legal-ai.client.ts` (the picker and `modelLabelOf`); `legal-intake.module.ts` (binds `GEMINI_CLIENT` to the picker for this module only, plus its own `AI_VOICE_PROVIDER` instance, so `AiToolsModule` is not imported and no route moves: importing it reordered `contract/openapi.json`, so it is not done); `legal-assistant.service.ts` and `legal-intake.service.ts` (`generatedBy` names the model that wrote the brief, one line each); `plan-setting-registry.ts` (`legal.ai_llm`, `legal.ai_provider`, `legal.ai_agent_id`); the agent client got only what was missing (`AgentSpec.allowOverrides`, `askAgent` `override` of prompt and model, and no voice named for a typed-only agent); the voice stand-in records overrides and takes queued replies; two new specs.

How it works. One agent at the provider ("Legal assistant", text-only override on, prompt and model overrides allowed, first message empty, privacy = `AGENT_PRIVACY`). Id from `legal.ai_agent_id`, else made by the first turn and logged so the owner can pin it; either way brought to the Hub's settings once per process. Every turn is a new text-only socket conversation that REPLACES the agent's prompt with the turn's own instruction (+ the JSON demand) and its model with `legal.ai_llm`; the earlier lines go as the transcript the Receptionist already sends. Sent: the instruction, the earlier lines and the message the Gemini call carried, nothing else (a spec checks the person's name, email, phone tail, account id and intake id are absent). Model: default `gemini-3-flash-preview`, the model Legal answers on today (the platform lists it; same family keeps answers alike; `gemini-2.5-flash` is not chosen, the platform removes it 30 Nov 2026); owner changes it with `legal.ai_llm`, no restart.

Structured answer: the platform has no structured output, so the Gemini schema is put in the prompt with a strict "one JSON object, nothing else" demand. The adapter accepts one JSON object (one markdown fence tolerated), otherwise throws "Legal chat returned unparseable JSON", and the services' own checks (matter, options, size, no em-dash) run unchanged on it. The brief goes through the same `normaliseBrief`. A provider 429 is written "HTTP 429" so the "assistant is busy" answer works as before. Keys unset: throws, the services answer as with an unavailable AI.

Privacy: provider side `retention_days` 1 and transcript and PII deletion on (`zero_retention_mode` is enterprise only), and the Hub deletes every conversation after its turn in the background (reads first, deletes only a finished one, counts it gone on a read of 404, 5 tries up to ~7 minutes, REC-DELETE's rule), also for a failed turn. No table (schema fenced), so a Hub restart in that window leaves the one-day retention as the backstop. Temperature is not settable per conversation, so the platform's own is used (Gemini ran at 0.3).

Checks (all on database `legal_eleven`, own mock WAWU ID on 14871, the voice stand-in): capability 1 `legal-assistant-elevenlabs.contract.spec.ts` (profile, brief, text-only, nothing about the person); 2 same spec (prose reply: 503 `assistant_unavailable`, same message, no assistant line, no draft); 3 `legal-ai-elevenlabs.spec.ts` (deleted after the turn, failed one too); 4 same spec (`legal.ai_provider=gemini` calls the Gemini client only, read per call). Gates 0 fail (139 warn, 88 accepted, as main), baseline ok, `contract/openapi.json` unchanged after two builds.
NOT RUN: any call to the real provider (the override keys and `llm` override as sent, real latency, real deletion timing); web-search-only research for the model list; the full backend suite (CI).

### Findings

- **F-1 medium, defect: agent sprawl, one new agent at the provider per restart.** `src/legal-intake/ai/elevenlabs-legal-ai.ts:117-131` (`agent()`): `this.ready` lives in the process, and with `legal.ai_agent_id` empty (its default, registry `plan-setting-registry.ts` `legal.ai_agent_id`) the first turn calls `createAgent` and only logs the id. PROVED with the voice stand-in and three fresh `ElevenLabsLegalAi` instances (three app boots) sharing one provider: 3 turns created agent-1, agent-2, agent-3 (3 creates, 0 reuse); the same three boots with the id pinned created 0 and patched 3 times. So every deploy and every restart leaves one more "Legal assistant" agent behind until the owner pins the id from a log line; two Hub instances booting together make two. Nothing breaks for the person, but the provider account fills with orphans nobody tracks, and the builder's own header comment ("set legal.ai_agent_id so a restart does not make another") admits the gap. Smallest sound fix, any one of: (a) before `createAgent`, list the provider's agents and reuse the one named exactly "Legal assistant" (needs a list-by-name call on `AiVoiceProvider`, none exists today); (b) have the Hub save the made id into `legal.ai_agent_id` itself (`PlanSettingsService.set` needs an `AdminActor`, so this needs a small system-actor write, and a race note for two instances); (c) at minimum, refuse to make an agent in production and say so in the deploy note, so the owner pins the id before the first deploy (the builder's task file does not tell the owner to). It blocks merge in my grading because the lead named it the main worry and (a) or (b) is a few lines; (c) alone would make it a low.
- **F-2 low (test-gap note): strict JSON read is stricter than the code it feeds.** `elevenlabs-legal-ai.ts:58-70` (`readJsonObject`) tolerates one markdown fence only. A reply of text then a JSON object, which `parseTurn` (`legal-assistant-prompt.ts:259-274`, takes the first `{` to the last `}`) would have accepted, fails the turn with the unavailable message. The platform has no JSON mode, so a model preamble on the first real runs is plausible. Not a wrong answer, a lower success rate; the fix is to pass the reply on to `parseTurn` and `normaliseBrief` without the pre-check, or to cut from the first `{` to the last `}` the same way. Test that would kill it: prose plus JSON must succeed on chat.
- **F-3 low, unproven: the first `agent_response` ends a turn.** `http-voice-provider.ts` `askAgent` (around line 2305) resolves on the first `agent_response` event. If the real platform splits a long reply (a long brief JSON) into more than one event, the JSON is cut and the turn fails closed (unavailable). Same code the Receptionist uses for short chat replies. Only the first real run shows it.
- **F-4 low, deploy note: the default flips legal on deploy.** `legal.ai_provider` defaults to `elevenlabs`. A host without `AI_VOICE_BASE_URL` and `AI_VOICE_API_KEY` answers legal with today's AI-unavailable message even though its Gemini key works (`ask()` throws "AI_VOICE_API_KEY is not set"). Tell the owner to check those two keys, or set `legal.ai_provider=gemini` first, before deploying.
