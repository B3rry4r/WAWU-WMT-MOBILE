**What the signature check proved (attack 2).** A throwaway spec (deleted) signed with the AWS SDK presigner through `signReadLink` and checked each link with my own SigV4 verifier (HMAC chain, canonical query sorted and encoded, host header, UNSIGNED-PAYLOAD) behind a local HTTP server. At 23:59:59, 00:00:00 the next day and 12:00 UTC: signature valid, `response-cache-control` is inside the signed query (dropping it or changing it gives 403), X-Amz-Date is the day start, X-Amz-Expires 604800. Life left at handout: 518401 s at 23:59:59, 604800 s at 00:00:00, 561600 s at noon; the link answers 200 at +6 d and +6 d 1 s from 23:59:59 and the server returned the cache header. A 900 s link is signed at the current second (date 22:20:42Z, not the day start) with no cache header. NOT proven: the real Spaces/Railway bucket accepting a signing date up to 24 h old (standard SigV4 behaviour, but not tried; never touched Spaces), and a real browser's second visit (header and byte-identical URL proven, no browser).

**Findings**
1. `low` (defect, shortened life): a link stored as-is and never re-signed (e.g. `recipient.service.ts:186` avatar, any `fileUrl` saved from a presign answer and read back raw) now dies between 6 d 1 s and 7 d after it was made, was 7 d. Anything read through `freshUrlFor` is unaffected (every read re-signs). App query stale time is 30 s, so no client holds a link that long.
2. `low` (cache of bytes that change): the only key rewritten in place is the VIDEO-PRIVACY clean (`video-privacy/clean-stored.ts`, same key, same length, only metadata patched). A link handed out before the clean (the presign `fileUrl`) carries `immutable`, so the uploader's own browser or image cache may keep the pre-clean bytes for a year. Other keys: avatars, covers, drafts and ad artwork use `randomUUID` keys (a replacement is a new key, so a new link); AI results are named by job id; `putCutPreview` re-puts the same name with bytes cut from the same source (identical). None of those links gets stale bytes.
3. `low` (policy): `immutable` is also on read links to paid full files (`unlock-wallet.service.ts:392`, `content-media.service.ts:136`), so a buyer's browser can keep bytes already delivered for a year after a refund or take-down. It is `private`, the same bytes the buyer already had, and course lessons (3600 s) get no header. Worth an owner glance, not a blocker.
