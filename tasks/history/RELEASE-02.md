1. **D-p3-2 (country blank after Save).** The builder's cause is plausible but inferred, not reproduced. Mock against real: the mock (`mock-wawu-id/server.js`) has only the legacy `POST /auth/register` (free-text `country` required, `countryCode` only if the body names it) and no email sign-up, so its tokens always carry `country: "Nigeria"`. The real WAWU ID's email and phone sign-up (`email-signup.service.ts`, `phone-signup.service.ts`, `signup-country.ts`) never stores the free text and always stores `countryCode` (the phone's country, else NG), so a real token is `country: null`, `countryCode: "NG"`. The Hub passes the whole token to `ProfileLocationService.me` and reads `countryCode` first (`wawuIdCountry`), so it derives NG from the real shape too (the existing `geo.contract.spec.ts` covers `me({ countryCode: 'NG' })`). The Hub records that country only when `GET /me/location` runs; `PATCH profile-fields` with a city alone never invents it, and never clears it. So a blank Country after Save needs either a Hub that had not yet learned the country when M8 read (a `/me/location` call that was late, dropped or never made: `PlaceBridge` asks once per sign-in) or an M8 draft that opened before the Hub learned it. The fix covers both: `fetchFieldsWithPlace` asks `/me/location` once when the Hub holds no country and reads again, and `heldCountry` takes the Hub's country into the form and the saved copy when neither holds one (the added tests are in the 481). It sends no country the person did not choose. What is not shown: the audit's exact state on the real WAWU ID. If Country is still blank on the real stack, the next place to look is whether `/me/location` answers a country for that token; nothing in the code read says it would not. Low (risk): re-walk on the real WAWU ID at the next CHECK pass.
