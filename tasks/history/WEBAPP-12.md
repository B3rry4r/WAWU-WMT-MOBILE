Findings:
1. **medium, defect: a tab open across a deploy cannot open a route it had not opened yet.** Each route is now its own hashed file. After a deploy the old file is gone, and the host answers the missing file with `index.html` (the rewrite), which the browser refuses as a script (`nosniff`, `Refused to execute script ... MIME type`, `AsyncRequireError`). Reproduced: loaded Today, removed every chunk not yet loaded, tapped Search: the app's "Something went wrong. This screen could not open." with Try again and Go to Home, no blank page. Try again asks for the same missing file; only a browser reload recovers (index.html is no-cache, so a reload gets the new names). Before this change one file held every route, so such a tab kept working. It will be common: deploys come from main, and WEBAPP-11 installs the app as a long-lived window. Fix: on an `AsyncRequireError` reload the page once, or keep the previous deploy's chunks, or turn on the host's version pinning; add a test. Picture `/tmp/w12v/stale-2-after-click.png`.
2. **medium, defect (privacy hardening, not reachable through any app screen): the worker serves a held picture for any request that carries its path and any signature, and nothing clears the cache at sign-out.** Account A drew a paid piece's full picture, session switched to B (no entitlement): B's own screens did not ask for it, but an image request from B's page to the same path with `X-Amz-Signature=junk`, and with an expired date, was answered with A's full picture (`LOADED`, `/tmp/w12v/swtest2.json`). The Hub's signed link is the entitlement; the worker drops the signature from its key, so the entitlement stops being checked once the picture is held. Today B cannot learn the path (uuid, B's Hub answers `null`), but a refunded or removed entitlement, a shared browser and the cache viewer all leave the picture reachable. The builder's known low (up to 120 pictures after sign-out) is the same fact. Fix: delete `wmt-pictures-v1` at sign-out and when the account changes (`caches.delete` from the web sign-out path, SHARED-CHANGES row if `src/api` is touched), and a test that a picture held for A is not answered after sign-out.
3. **low, defect: the bound is a count, not bytes.** 120 pictures of up to 4.7 MB (a free piece's preview is the whole photo) can hold about 560 MB on a visitor's disk; eviction is oldest stored, not oldest used. Add a byte budget or a smaller count for large pictures. Chromium's own quota is the only other limit.
4. **unclear (owner or lead): a creator still in the sign-up sequence (`GET /auth/signup/progress` says `creator_setup`) opens "Set up your account" on the branch, and Today on the base, same account and server (4 runs each way).** `startHref` in `src/features/shell/startHref.tsx` says `creator_setup` leads to `/creator-setup`, so the branch matches the code and the base looks like the odd one (a timing race the smaller first load changed). Confirm the intended behaviour; no change asked of this task. Once "Later" was tapped (`step: done`) both opened Today.
5. **low, test-gap note:** the worker's tests run it against a fake browser, so they do not kill a mutant that caches a 403 or an non-image, or one that skips the `X-Amz-Signature` check: cover the ones shown here (403 not cached, non-image not cached, a held picture not answered after sign-out).
