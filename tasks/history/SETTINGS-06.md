### Findings
1. HIGH. A wallet is left frozen with no deletion scheduled when the provider fails after the freeze. account.service.ts:79-81: freeze succeeds, then `balanceOf` throws 503 (A1), or the freeze answer is lost after Fintava froze it (A2; the interface comment even says recordMayExist). Repro: attack spec A1, A2 (frozen:true, rows 0).
2. HIGH. A cancel can be answered "restored" while the data is deleted. (a) sweep vs cancel (A3): sweep reads the due row, reads the balance, and purges with no re-check of status; a cancel in that window returns cancelled:true, walletUnfrozen:true, then the sweep deletes everything and writes status purged over cancelled (account-deletion-sweep.service.ts:85, 115, 134, 153; cancel at account.service.ts:180-192). (b) WAWU ID down at the end (A10): Hub data purged, row stays scheduled with identity_service; the person signs in, cancel answers cancelled:true, unfreezes, restores 0 pieces; the row is now cancelled so the sweep never finishes, and the account is an empty shell never anonymised. Irreversible. Fix: claim the row (conditional update scheduled to purging) before any delete, make cancel refuse once purging, and make the final write conditional.
3. MEDIUM. The sweep marks a deletion purged although the purge failed on rows (A8): a creator whose content was sold cannot lose ContentPiece (Purchase.content is Restrict); AccountPurgeService swallows the error per table and returns only pointsLeft, so the row is marked purged, WAWU ID is told to anonymise, and the piece (title, description, preview URL) stays under the old id. Purge behaviour itself is pre-existing on main (unchanged file); the false "purged" is this task's sweep. Fix: have purge report failed tables and keep the row blocked, or anonymise sold content.
4. LOW. Money check and freeze are not atomic with a money action (A6): an open hold created while the balance is being read still lets DELETE schedule. The sweep's final check then keeps the account (blocked by open_hold), so no money is lost. Pending ledger entries (a withdrawal just made to empty the wallet, FintavaLedgerEntry pending) are not a blocker; a failed one would reverse into the frozen wallet and hold the purge back.
5. LOW. Cancel after a provider switch (N2): scheduled under Fintava (frozen), cancelled with a provider that cannot unfreeze, the answer is cancelled:true, walletUnfrozen:false, walletFrozenAt is cleared and the wallet stays frozen at Fintava. The row's walletProvider is not used.
6. LOW. A wallet opened during the 30 days is not frozen (nothing refuses opening while deletion is scheduled); the final check blocks the purge if it holds money. Repeat DELETE after the date but before the sweep answers a past date. Web comments in src/lib/api/settings.ts:120,127 still say 48h.

**Round 2 (16 Oct 2026, Sonnet builder; backend `wmt/SETTINGS-06` @ 51cb282 with origin/main 18ac5f9 merged in; mobile docs only).** Fixes the verifier's findings 1 to 3. Findings 4 to 6 (lows) went to `tasks/SWEEP-MONEY.md` (rows L4 to L6).
- **Finding 1, high (a wallet left frozen with no deletion recorded):** `DELETE /account` reads the balance and the blockers before it freezes anything, so a refusal changes nothing. It then writes the deletion row (status `freezing`, with the wallet id) BEFORE the freeze call, freezes, reads the balance once more, and only then makes the row `scheduled` and hides the content, in one transaction under the row's lock. A failure after the freeze (balance unreadable, a lost freeze answer, money that arrived) lets the wallet go and closes the row; if the unfreeze fails too, the `freezing` row stays, and either `cancel-deletion` or a new `DELETE /account` unfreezes from it (a retry that finds money unfreezes first, then refuses with 409, so the wallet works). A cancel that lands while the request is freezing wins: the request ends with nothing scheduled and nothing hidden.
- **Finding 2, high (a cancel answered restored while data is deleted):** the sweep checks the money, then claims the row with one conditional update (`scheduled` to `purging`); nothing is deleted before the claim. A cancel that finished first makes the claim find nothing, and the pass leaves the account alone. Every later write names the status it expects. If WAWU ID is down at the end, the row stays `purging` with `purgeBlockedBy: identity_service` and the next pass finishes it; it is never `cancelled`.

A content piece with a purchase cannot be deleted (`Purchase.content` is Restrict): it is hidden (`removed`) and loses its title (becomes "Removed content"), description, preview and file URLs, tags, specializations, slug, and its lessons, frames and detail rows go; `AccountDeletion.purgeNote` records how many.
