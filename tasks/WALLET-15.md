## Goal

Every fee shown before paying comes from the server, never from the app.

## Scope

GET a fee quote, from configuration set per R-10 (Fintava's charge plus WAWU's fee), for:
- a purchase (unlock, tip, tick, ticket, paid DM, credits, course, legal service): Fintava's balance-transfer
  charge by amount band, no WAWU fee;
- a bill: Fintava's bill charge by category (₦100 electricity or cable, ₦0 airtime or data) plus WAWU's bill fee
  (₦0 today), and the payer's balance-transfer charge into WAWU's wallet (R-31);
- a send to a WAWU user: Fintava's balance-transfer charge by band + WAWU's ₦10;
- a send or withdrawal to a bank: ₦40 + ₦25.
Card top-up and card order are added by WALLET-25 and WALLET-31 after launch. The rates are the dashboard ones in
`docs/fintava/fees.md` (final).

Payouts out of Fintava don't work in the sandbox yet: bank sends and the airtime, data and electricity purchases answer `400 "Unable to find customers"`, and cable answers "service not currently available", with nothing debited (`docs/fintava/sandbox/README.md`, "The blocker"). Unblocked when a ₦100 `POST /bank/credit/merchant` to the sandbox stub `0123456789`/`000013` stops answering "Unable to find customers" (question 17 in `docs/fintava/naira-api.md`). Build and unit-test meanwhile; report the bank-send and bill checks NOT RUN with that reason until then.

## Fintava facts

From `docs/fintava/naira-api.md`; a real sandbox response overrides it.

The user pays Fintava's fee plus WAWU's fee (R-10). The quote is Fintava's fee for that action plus WAWU's fee from config, shown as one total with both parts in the breakdown. Fintava's charges are in `docs/fintava/fees.md`. WAWU's fee is set as a merchant charge in Fintava's dashboard; config holds the same numbers so the quote shows the total before the user confirms.

**Findings**
1. Not a defect: no wallet can reach it. For `bank_transfer` near 2^53, `maximumKobo` is 1 kobo low: 9007199254734490, where 9007199254734491 still fits (`band-edges.txt`). The cause is float rounding in `largestAmountUnder` once `cap + fee` passes 2^53. The amounts involved are about ₦90 trillion.
2. Test gap: mutants M10 and M13 survive. With the default cap, no test exercises the step-down loop in `largestAmountUnder`. It matters when `MERCHANT_MAX_PER_TXN_KOBO` sits near the band edge: at 501000 the loop answers 498675, and without it the answer would be 499425, which does not fit. No test uses a `FEE_QUOTE_KEY` of 8 to 31 characters.
3. Not a defect: hardening for the paying tasks. Base64url decoding is lenient, so a signature with a different last character, a trailing `==`, or a `*` inside it is still honoured. The claims cannot change, so this is not a forgery. But WALLET-07, WALLET-09 and MONEY-17 must never use the token string as a once-only or idempotency key. Also, `FEE_QUOTE_KEY` is checked for length only, so `aaaa…` (32 characters) is accepted. And `check()` on a bill with no category throws a plain `Error` (a 500), not a 400; only a server-side caller can reach it.
4. Production, unclear (ops): `deploy/README.md`'s `hub-api.env` list does not name `FEE_QUOTE_KEY`. The droplet runs one process, so the random key is correct today, and nothing calls `check()` yet. Once WALLET-07, WALLET-09 or MONEY-17 call it, every deploy and crash restart turns open quotes into one re-quote. A second process or instance would refuse every other request's quote. Production needs `FEE_QUOTE_KEY` (`openssl rand -hex 32`) in `/etc/wawu/hub-api.env` before the first paying task merges, and it is mandatory before more than one process answers.
