## Owner ruling (6 Oct 2026)

Fintava is being removed (Nuvion replaces it, and Nuvion has no SMS). The owner, asked what sign-up does without SMS:

> "same thing for SMS... we'd use emails as we've been using"

Recorded by the lead as DECISIONS.md R-39 ("No SMS: codes go by email, as before. Sign-up verification moves to the email code (AUTH-07)"); this task adds no ruling of its own. Meaning:

- Sign-up's required verification is a 6-digit code mailed to the email typed on A3, sent the way WAWU ID already sends email (Resend). No text message is sent at sign-up.
- The phone number is still asked on A3 (it is used later) but is not verified by a code at sign-up.
- Reversible, additive: one WAWU ID setting, `SIGNUP_VERIFY_CHANNEL=phone|email`. **Default `phone` (lead ruling, 10 Oct 2026, round 2): today's behaviour, so deploying WAWU ID changes nothing by itself.** `email` is switched on by the release steps below and answers the old phone-code routes 409 `SIGNUP_CHANNEL_DISABLED`; `sms`, this value's name in round 1, is still read as `phone`. The Fintava SMS provider and every phone-code route stay in the code. No route is removed.

## Goal

A user signs up with email, phone and password, receives a 6-digit code by email, enters it on A4, and is signed in. Nothing is texted. This holds once the release steps below have switched WAWU ID to `email`; until then WAWU ID texts as it does today. The owner can roll back by changing one environment variable.

## Scope

- wawu-id: the sign-up sequence's code step, under the setting; a new email-code resend and confirm route pair; a nullable `channel` column on `phone_verifications` (additive migration).
- Mobile: A3, A4 and A15 copy (channel words only), the sign-up flow client, the contract sync, the preview harness, tests, BRIEF and DECISIONS entries.
- Round 2 (lead rulings, 10 Oct 2026): nobody holds a phone number they have not proven (wawu-id sign-up services, and the three routes that send a code to an account's number), the default of the setting, the resend route's refused mail, three missing specs. No migration and no schema change.
- Not touched: anything in the Hub, `src/fintava`, `src/money`, wallet, PIN, payment or KYC code.

## Release steps (lead ruling, 10 Oct 2026; also in wawu-id `deploy/ENV.md` and `WAWUAfrica_API_Contracts.md`)

The setting's default is `phone`, today's behaviour, so the order of release matters and each step is checkable:

1. Deploy WAWU ID with `SIGNUP_VERIFY_CHANNEL` unset or `phone`. Nothing changes for anyone: the sign-up texts as it does now.
2. Release the app build with email codes to testers. Older builds, and sign-ups waiting on a text, keep working while the setting is `phone`. The new build draws the texted screens ("Verify your phone", "Sent by SMS to ...") because WAWU ID answers with no `channel`; only A3's line says email (BRIEF, A4).
3. Confirm Resend in production: `RESEND_API_KEY` is set on WAWU ID and the sending domain is verified, shown by a real mail arriving in a real mailbox (for example a forgot-password link asked for with `method: email`, for an account whose address is the person's own). G-213 (the sender and wording) is the owner's.
4. Set `SIGNUP_VERIFY_CHANNEL=email` and restart WAWU ID.
5. From then an older app build and any sign-up still waiting on a text are refused (409 `SIGNUP_CHANNEL_DISABLED`) and start again at A3. Keep the time between steps 2 and 4 short, because A3's line says email while WAWU ID still texts.

Rolling back is setting `phone` and restarting WAWU ID.
