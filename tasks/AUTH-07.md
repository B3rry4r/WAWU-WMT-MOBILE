## Owner ruling (6 Oct 2026)

Fintava is being removed (Nuvion replaces it, and Nuvion has no SMS). The owner, asked what sign-up does without SMS:

> "same thing for SMS... we'd use emails as we've been using"

Recorded by the lead as DECISIONS.md R-39 ("No SMS: codes go by email, as before. Sign-up verification moves to the email code (AUTH-07)"); this task adds no ruling of its own. Meaning:

- Sign-up's required verification is a 6-digit code mailed to the email typed on A3, sent the way WAWU ID already sends email (Resend). No text message is sent at sign-up.
- The phone number is still asked on A3 (it is used later) but is not verified by a code at sign-up.
- Reversible, additive: one WAWU ID setting, `SIGNUP_VERIFY_CHANNEL=email|sms` (default `email`). `sms` restores today's behaviour exactly; `email` answers the old phone-code routes 409 `SIGNUP_CHANNEL_DISABLED`. The Fintava SMS provider and every phone-code route stay in the code. No route is removed.

## Goal

A user signs up with email, phone and password, receives a 6-digit code by email, enters it on A4, and is signed in. Nothing is texted. The owner can roll back by changing one environment variable.

### Findings

- **F1 · unclear (owner), high.** *A stranger can hold anyone's phone number for good, and the phone is no longer proven when the BVN check reads it.* With `email`, a sign-up proves the mailbox only, so anyone can sign up with a victim's phone and their own email, confirm with the code mailed to themselves, and own that number: the victim's own sign-up then gets 409 "An account with this email or phone already exists" with no way round it (`t8`: attacker confirmed 200, victim 409, the row holds the victim's number with `phone_verified_at` empty; on main the same attempt cannot confirm without the victim's text and the victim's later sign-up replaces the pending row). Costs the attacker one free mailbox per number, within 100 sign-ups a day per address. Second half: the Hub's A14 check compares the BVN's phone with this account's phone, which a text used to prove. The builder recorded both as G-212 and chose "typed and unproven" (decision 3), so this is not a defect against the ruling, but it is a security regression the ruling's text did not weigh. A cheap fix the code already has the shape for: let a sign-up take a phone held by an account whose `phone_verified_at` is empty, the way an unproven email is claimable today. Owner decision before `email` goes live, and before the wallet rebuild relies on the phone (R-39 says KYC may drop the selfie).
- **F2 · unclear (lead, release order), medium.** The default is `email`. With no `SIGNUP_VERIFY_CHANNEL` set, production wawu-id flips from texts to mail the moment it deploys: (a) if `RESEND_API_KEY` or a verified sending domain is missing there, sign-up answers 503 `EMAIL_NOT_CONFIGURED` for everyone; (b) an app build in the field from before this task calls the phone routes and gets 409 `SIGNUP_CHANNEL_DISABLED`; (c) texted sign-ups pending at the deploy hit the same 409 (the new app shows "This sign-up needs to start again"). The other order is safe: the new app against a wawu-id still on `sms` (or on main) works, and only A3's line says email (BRIEF notes it). Suggest: ship the app first, confirm Resend on wawu-id with one real send to the owner's address (G-213, NOT RUN here), then deploy wawu-id.
- **F3 · low.** `POST /auth/signup/email-code/start` answers 200 even when Resend refuses (the mail is sent after the answer so real and made-up secrets cost the same, as on the phone route), and it keeps the person's 60 s gap and one of the 5 mails a day (only the global mail is given back). The stated check "a Resend error gives 503 and the quota is returned" holds for sign-up, not for resend: the user sees "We sent a new code" and nothing arrives; they can ask again after the gap. Same shape as the phone resend; recorded so nobody expects a 503 there.
- **F4 · low.** Brief expected `wawu-id CLAUDE.md`; there is none (README only). The builder's task file says so correctly.
- **F5 · low (test gap).** Three wawu-id behaviours are not held by any spec: the confirm limit per address on the mailed route, the per-email daily limit on sign-up, and the day and global counts returned after a refused mail. A live run catches each (my `t2`, `t11`), the jest suite does not (mutants M1, M10, M11).
