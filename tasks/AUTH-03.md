## Goal

A4 verifies the phone. The canvas never verifies email, but login refuses unverified email today, so a new user could never sign back in.

## Scope

Phone code at registration; fix the login rule so a phone-verified account can sign in even without a verified email (the design never verifies email, but login refuses it today); store account type (A2). No BVN here (R-6); occupation is asked on A5, inside Open your wallet, and stored by KYC-01.

BACKEND_GAPS G-2 (register issues tokens before anything is confirmed) is this task's to settle: tokens are issued once the sign-up proof the design draws, the phone code on A4, is done.

## Fintava facts

From `docs/fintava/naira-api.md`; a real sandbox response overrides it.

Fintava has `GET /compliance/verify/phone-number` and `POST /sms/send`. Codes go by SMS through `POST /sms/send` (₦7 each, `docs/fintava/fees.md`); MONEY-14 reuses the same route for PIN resets.

### Findings

**F-1 · defect · medium. `phone/verify/start` and `confirm` work for every existing account, not only mobile sign-ups.** Contract text says a phone "already proven or unknown is never texted". Every row that existed before the migration has `phone_verified_at` NULL, so `start` texts it and `confirm` with that code answers 200 with a session and no password (`E/v2c.txt`: legacy web account with a confirmed email, texted, confirmed, session issued, `phone_verified_at` stamped). This is a new password-less sign-in for the whole user base, and a number typed wrongly or recycled at web sign-up (the web never proves the phone) reaches the old user's account. It is no weaker than the existing `POST /auth/otp/verify` (no attempt limit at all there), but nobody ruled it in and the contract says the opposite. Needs the owner: limit start/confirm to accounts created by `signup` (for example no confirmed email and no earlier login), or accept it in writing.

**F-2 · defect · medium. ### Findings

**D-1 · defect · high. A later sign-up with a pending sign-up's phone replaces it, and the person who confirms with the newest text ends up signed in to the attacker's account.** `E/v2e.txt` S7. Victim signs up (email V, phone P) and is waiting for the code. Attacker (knows only P, 60 s later) signs up with attacker email A, password known to the attacker, phone P: the victim's pending row is deleted, a new code goes to P. The victim gets two texts, types the newest, `confirm` answers 200 with a session whose user is `attacker7@x.com`; the attacker can log in to that account (200). Everything the victim then does (wallet, KYC, money) is in an account the attacker controls. The same works with the victim's own email (builder default 3: a repeat sign-up for the same email and phone replaces the pending one and its new password wins). Cause: `confirm` is keyed by phone only and the supersede rule deletes any unproven row on any later sign-up, which is more than R-36's "releases after 24 hours". **D-2 · defect · medium. The third capability check fails: a never-confirmed mobile sign-up can still get a token the Hub accepts.** Through `/auth/email/verify/start` + `/confirm` always, and through `/auth/otp/start` + `/otp/verify` while WhatsApp is unconfigured (code mailed to the account's email). **D-3 · defect · medium (a recorded agent default whose attack works; owner may override).
