# FIX-06 · An admin's unlist cannot be undone by the professional

## Goal

Found by PROS-03's independent verifier (8 Oct 2026): the admin "unlist" route writes the same `listed = false` as a professional's own Hide, so the professional can Show again a listing an admin pulled. An admin's decision must hold until an admin reverses it.

## Scope

Keep the admin's unlist apart from the person's Hide (for example its own column or state with who set it and when), so the person's Show cannot list a profile an admin unlisted, and the person's P8 says it was taken down (the app's wording comes from PROS-03; this task returns a state the app can read). Existing rows keep their meaning: a migration with a backfill that treats today's `listed = false` rows as the person's own Hide unless an admin audit row says otherwise. If the admin route is on the protected list, its answers stay the same; say which routes are protected.

## Capability checks

- [ ] An admin unlists a listing; the professional's Show answers a refusal and the directory still hides it.
- [ ] An admin lists it again; the professional can Hide and Show as before.
- [ ] A professional's own Hide and Show behave exactly as today.
- [ ] Protected routes 253/253; any web caller of the admin route sees the same answer.

### Defects (open)

- **D1 · defect, low (V2 races, V4): an approve or a reject that read the application before another admin's decision still writes `listed` over a standing takedown.** The builder's map says approve and reject "cannot touch an approved listing, so none can undo a takedown". Both check `status === 'pending'` on a plain read, approve then calls WAWU ID, and both write with no lock and no re-check (`admin-professional-review.service.ts` `approve`, `reject`), so a decision that read `pending` before a concurrent approve committed still lands after an unlist. Reproduce (fresh branch database, real routes): (a) over plain HTTP with no lock, `bin/race_approve_free.py b 80 <out> family_lifestyle`: approve as superadmin and as a reviewer fired together, an unlist 0 to 60 ms later; 7 of 80 rounds answer 200, 200, 200 and end with the takedown standing and `listed = true`: `GET /professionals/:id` 200 and in both directories, while P8 says `taken_down` and the owner's Show answers 409. With a psql session holding the row for a moment only to line the three up (`bin/race_approve.py`), 3 of 20. (b) Approve, unlist, then a reject that read `pending` before the approve committed (`bin/race_reject.py`, the row held for a moment to order them): 8 of 8 rounds end `rejected` with the takedown still standing; the person applies again (201) and an admin approves (200): `listed = true`, public profile 200, P8 `taken_down`, the owner's Show 409. Rare (two admins deciding one application inside the WAWU ID call's window while a third pulls it), but it breaks "a listing never ends shown while a takedown stands", and (b) leaves a takedown row that a later, ordinary approve walks past. Fix shape is the builder's call: approve and reject lock the row and re-check `pending` inside the transaction (or write with `where: { id, status: 'pending' }` and answer 409 when nothing changed), and an approve never sets `listed` true over a standing takedown.

### The decisions

- **A Hide while down is kept:** keep; it is today's Hide answer and the owner's last word on relist (all 50 Hide and relist race rounds end hidden).
- **The first takedown stays on record:** keep for a second unlist while down. Note that a takedown after a lift overwrites the row, so only the latest takedown and its lift are on record; if the owner wants a takedown history this becomes an append-only record.
