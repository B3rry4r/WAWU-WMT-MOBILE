## Goal

Today `PUT /events/:id/tickets` lets a host whose verification has lapsed, or who was never verified, change the ticket tiers and prices of an event an admin already approved, and the event stays public with no second look. POST and PATCH /events already refuse such a host and send edits back to review. The ticket route must follow the same two rules.

## Scope

1. `PUT /events/:id/tickets` runs the same hosting gate as POST and PATCH /events: same 403 reasons and the same error shape (`account_type_required`, `verification_required`), checked before anything is written.
2. A tier change on a `published` event sets the event back to `pending`, as a PATCH does today: strangers get 404 until an admin approves it again, and the host still reads it. An edit to a `pending` or `rejected` event leaves it `pending`.
3. Once any ticket on the event is sold, the existing 409 stays exactly as it is (it is checked first, and nothing changes).
4. A request that changes nothing (the same tiers sent again) changes nothing, including the status.
5. Additive only in shape: no field renamed, retyped or removed. This is a deliberate behaviour change to a protected route, ruled by the owner (R-40). If the protected suite (`scripts/protected-routes/run.sh`) has a test that asserts the old behaviour (an unverified host succeeding, or a published event staying published after a tier change), do NOT edit the test, the lock or the registry: stop and report the test name to the lead, who takes it to the owner.

## Capability checks

- A verified host changes a tier price on an approved event: 200, the event is `pending`, a stranger gets 404, an admin approves it, and the new price is public.
- The same host after their tick lapses: 403 `verification_required`, nothing written, the event stays public at the old price.
- A buyer account and a never-verified creator: 403 with the right reason, nothing written.
- With one ticket sold: 409 as today, nothing written.
- The web's own event pages and checkout still read the event as before (V3 byte compare on a verified host's flow).

### Findings

- **D1 · defect (race).** PUT /events/:id/tickets can undo an admin's takedown. `setTicketTypes` reads `status` at the start, then (after the gate, the sold check and the no-change read) writes `BACK_TO_REVIEW` with an unconditional `event.update`. If an admin removes the event in between, the takedown is overwritten with `pending`: the event leaves `removed`, re-enters the queue, and an approve publishes it, which bypasses restore. Reproduction (`race.js`, branch Hub): a published event of a verified host; send `PUT /events/:id/tickets` (₦9,200) and `POST /admin/events/:id/remove` together: 37 of 40 trials end with remove 200 and status `pending`. Control: remove first, then PUT, stays `removed`. On main the same race leaves `removed` (10 of 10), because main's PUT never writes the status, so this path is new with this task and breaks the ruled rule that a removed event stays removed. PATCH /events/:id has had the same pattern on main (5 of 10 trials end `pending` after a 200 remove), outside this task. Unblocked when the back-to-review write is conditional on the status it was decided from (for example `updateMany` where `status in (published, rejected, pending)`, or the event row locked at the start of an interactive transaction) and a spec races PUT against remove.
- **O1 · note.** The lock records `ticketTypes` as `[]` (the queued event in the suite has no tiers), which matches any array, so the protected suite does not pin the tier element shape, and it has no unverified-host PUT probe and no non-published tiers read. M1, M5 and M6 survive the suite; the new spec kills each. Nothing to change for this task.
- **O2 · pre-existing.** Concurrent PUTs to one event can leave more tier rows than any request sent (`deleteMany` then `createMany` at read committed): branch 10 rows, main 7 and 4. On the branch the event is always `pending` afterwards, so a reviewer sees them before they are public. Taking the event row lock first, as for D1, also fixes this.
- **O3 · note.** A PUT that passed the gate a moment before the tick lapsed still writes; it is the same check-then-write PATCH and POST use, and every such write left the event in review.
- **O4 · note, not in the builder's report.** The regenerated `contract/openapi.json` also reorders the `category` enum of `EventView` and `EventOptionsView` ("community" moves from first to eighth), most likely from the new module import changing the compiler's type order. Same values, no runtime change (GET /events/options byte-identical); mobile's generated client will show the reorder at the next sync.
- **NOT RUN.** The full backend suite: the network namespace it needs (for its :4001 stand-in) was refused to this session; unblocked by running it in a namespace (or with WAWU_ID_BASE_URL on a free port) from a session allowed to. `hub-rate-limits.contract.spec.ts`: part of that run. Real WAWU ID (stand-in used). The `relock-approved` label (owner only; its effect was checked with `ci-check.sh ... 1`).

**Verdict: building.** One open defect (D1). Everything else the brief lists holds, and the lock change is exactly the four parts named.
