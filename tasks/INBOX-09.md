## Goal

Creators who leave too many paid questions unanswered are warned, then paused for 7 days (R-13). Additive only.

## Scope

Rolling 30-day unanswered rate, warning and switch-off per R-13, enforced when sending and shown on the profile.

## Capability checks

- [ ] A creator at 21% unanswered over 30 days is warned once; at 31% paid questions switch off for 7 days and a fan sees I8. The thresholds (20% and 30%) come from config.

**Findings**

1. **defect** (latent scale, low): the sweep never reaches creators beyond the first 500. `PaidDmPauseService.sweep()` takes `distinct creatorWawuId` with `take: 500` and no `orderBy`, and the flagged list is also `take: 500`. Creators already paused or warned keep their misses in the window, so the same 500 fill the list on every run. With 620 creators each holding one lapsed question, three consecutive runs each reached 500; 500 were paused and notified, 120 never were (my `SWEEP-SCALE` probe). Send-time enforcement still works for those 120 (it evaluates on every send), but their warning and pause notification and their write-back at the end of a pause never happen from the sweep, which is the sweep's whole job ("without anyone looking"). Fix by paging through all candidates (cursor on `creatorWawuId`) or ordering by least recently checked.
2. **unclear** (owner, G-77, already filed, `PROVISIONAL` present): R-13 says only "warned at 20% unanswered paid questions and paid messages pause for 7 days at 30%". It names no minimum count and no basis, so the default minimum of 1 is the builder's literal reading: a creator's first lapsed question reads 100% and pauses paid messages for 7 days (my `MIN-1` test: 1 missed gives `paused`, 100%). Nothing in R-13 or the task text decides otherwise, so it is not a defect, but it is a harsh outcome the owner should settle before launch. Same entry covers the basis (share of questions sent in the last 30 days whose outcome is known: answered, or past their deadline; questions still inside their window count for nothing yet) and "at or over" (the canvas copy says "over 20%" and "Past 30%"; R-13 says "at", R-13 outranks the canvas; only the exact line differs). All three are as G-77 says; I checked each against the code and boundaries.
3. **differs-for-recorded-reason**: `GET /dm/response-stats` (live route, web and dashboard read it) now reports `penaltyState` `warned` or `disabled_7d`, the stored percentage and `dmDisabledUntil` for a creator at or over a line, once the standing has been evaluated (a send attempt, either new read, or the sweep). The tracker row is the state the task and R-13 give ("shown on the profile", `CreatorNoResponseTracker` already holds the three fields). Shape and every value for any creator under 20% are unchanged (scenarios A to D, I, J, seeded creators identical). SHARED-CHANGES `INBOX-09 #1`.
4. **unclear** (task text "shown on the profile"): the profile routes the web calls (`GET /users/:id/public-profile`, professional routes) are unchanged for everyone, so they still say a paused creator takes paid messages (identical on main and branch in my scenarios, G-78). The signal for I8 is the new availability route. That satisfies the check "a fan sees I8" through the app, but the task scope says "shown on the profile"; the orchestrator or owner should confirm the new route is the intended reading. The web shows its generic error on the 403 until it is ported (G-78).
5. **unclear** (minor, no user effect): the builder's "the tracker row is only written when the standing moves" is slightly off. Evaluating a creator with no row inserts a zero row first (needed for the row lock; `GET /dm/response-stats` already upserts the same zero row, so no response changes), and a row stored as `warned` or `disabled_7d` that no longer matches the questions is rewritten to `none` and 0 on the first evaluation (scenarios K and M; nothing wrote such rows before this task except seeds with `none`, so no live data is affected). Also `GET availability` by any signed-in user can cause that write and the creator's notification, harmless.
6. **unclear** (low): the notification is written after the transaction commits and `NotificationService.emit` swallows errors. Under concurrency it is exactly once per transition (proved above), but if that one insert fails, the state is already stored (`warned` or paused) and nothing retries it, so that transition has no notification. The builder's design decision; worth a line in G-77 or accepting.
7. **unclear** (not this task's, mobile): `OpenWalletScreen.test.tsx` "a user sees a loading view first..." times out at 5 s with a cold jest cache (`npx jest --clearCache` then `npx jest src/features/open-wallet` fails 1 of 54 every time; warm runs pass). The branch changes no file under `src/`, so main has the same cold-cache failure; it is why the builder's first mobile run was exit 1 and why the first `npm run check` in a clean worktree can fail. Belongs to the wallet task that owns that test.
8. **unclear** (low): the contract (`contract/openapi.json`) documents only the 200 of the two new routes and does not mention the 403 `paid_messages_paused` refusal on `POST /dm/{creatorWawuId}/send` (the route is unchanged in the contract by design, SHARED-CHANGES says so). The app reads the code from `reason.code` by convention (CONVENTIONS "decide on `reason.code`"); there is no generated type for it. Same as the other 403 reasons today.

Not run: nothing in the pass list. `scripts/local/smoke.sh` not run (not asked). My probe spec and driver are untracked and are not committed to either repo.
