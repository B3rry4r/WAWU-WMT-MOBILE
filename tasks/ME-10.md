### Findings

- **F1 · unclear (low, hardening).** A calendar-impossible cursor date is accepted: `m1.` plus base64 of `{"at":"2026-02-30T00:00:00.000Z","id":"x"}` answers 200 on all four lists (JS rolls it to 2 March). No 500, nothing leaks (it only filters the caller's own rows, exactly as any well-formed cursor does). One-line close: refuse when `new Date(at).toISOString() !== at` in `decodeMeCursor`. Not blocking.
- **F2 · unclear (low).** `PUT /me/lessons/:id/done` on a piece the caller bought but that is now `removed` answers 200 (reproduced live: status set to `removed`, buyer's PUT 200, the purchase still listed). The service's own comment says a piece not live is the same 404. The brief's rule (a hidden, blocked piece cannot be marked) holds. Decide which is meant and align the comment or the code.
- **F3 · unclear (low).** A Purchase is dated by `purchasedAt`, which is when the checkout row was created (nothing rewrites it on completion; `Purchase` has no completion time). A charge begun before Lagos midnight and verified after it counts in the earlier month; paid questions are dated by `respondedAt`, so the two streams use different clocks. `GET /content/mine/earnings` has the same limit but is not monthly. Needs a completion timestamp to close; worth a gap line next to G-206.
- **F4 · differs-for-recorded-reason (cite: builder Default 4 and G-206).** Event ticket sales are not in earnings, as in `GET /content/mine/earnings`. Also `review_received` now appears in the web's `GET /notifications` as a new kind value (shape unchanged, bytes identical for the rows that exist); the web's union does not list it (G-205), so the web renders an unknown kind until it is told.
- **F5 · note.** `PUT /me/saved/creators/:wawuId` accepts any person with a profile (a buyer account too), not only creator accounts. Matches "a creator while they have a profile" in the service comment.
