## Goal

Replies, refunds, money in and join decisions need to reach a phone.

## Scope

Device token registration and removal; a sender behind the existing notification service that respects settings; Expo push.

Categories follow the user's Z3 switches (SETTINGS-07). The phone side (permission, token, tap) is INBOX-21. Android push needs the owner's FCM credentials uploaded to Expo (owner input).

V10 runs on a real Android phone only (DECISIONS R-24).

## Capability checks

- [ ] A notification sent to a registered push token is accepted by Expo's push service, and its receipt reports it delivered within a minute (the phone side is checked in INBOX-21).
- [ ] A category the user turned off in Z3 (SETTINGS-07) is not sent.
- [ ] A dead token is cleaned up.

**Defects (open).**
- **D1 defect: a crash or restart mid-pass silently loses the whole claimed batch.** Reproduction (`exp-crash.js`, `crash-accepted.txt`, `crash-never.txt`): Hub on :5401 with `PUSH_ENABLED=true`, stand-in on :5404, 40 `new_follower` notifications for a person with 2 phones inserted; poll until `PushDelivery` holds `sending` rows; `kill -9` the Hub (once at +1.4 s, once at +7.9 s); restart; wait 150 s. Both runs: 80 of 80 deliveries `failed / send_interrupted`, stand-in saw 0 requests and 0 messages, nothing resent. Cause: `claim()` marks up to 500 rows `sending` in one statement, then does one switch query per row and sends in chunks, so the "claimed but not yet on the wire" window is seconds long; `reapStuck()` fails every `sending` row older than 120 s and treats it as "Expo may have taken it". A surviving second Hub only reaps, it does not take the rows over. The backend deploys on every merge to main, so every restart can drop a batch. No duplicates occurred in any run (a lost answer is never resent), so the policy is at-most-once; the check asked for neither loss nor duplicates. A fix is a separate `claimed` state that expires back to `pending`, with `sending` set only just before the HTTP request. A hung Expo gives the same loss (4 of 4 in `states-timeout.txt`).
- **D2 defect: a blocked person's activity is still pushed to the blocker, and the push carries the blocked person's id.** Reproduction (`exp-live.js`, `live-out.txt`): B has a phone; A `POST /creators/B/follow` (201); B `POST /settings/privacy/blocked` for A (201) immediately; within one sweep the stand-in receives title "New follower", body "Someone started following you.", `data.target = {kind:"profile", id:<A's WAWU id>}`. The in-app list for B hides the same row (`GET /me/notifications`: `actor:null`, `target:null`, SETTINGS-04), and a follow after the block is refused (403). `skipReason` has no block check and `buildMessage` always copies the target. The lock-screen words are anonymous, but the payload names the blocked person and a tap opens their profile. Anything written before a block and still inside the 15-minute look-back or a retry reaches the phone.
- **D3 defect (low): `push-token.contract.spec.ts` deletes a seeded row and does not put it back.** Lines 359 to 361 and 377 to 379 `deleteMany` the seeded follow edge from the plain user to the basic creator.
