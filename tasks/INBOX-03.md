## Goal

Replies, refunds, money in and join decisions need to reach a phone.

## Scope

Device token registration and removal; a sender behind the existing notification service that respects settings; Expo push.

Categories follow the user's Z3 switches (SETTINGS-07). The phone side (permission, token, tap) is INBOX-21. Android push needs the owner's FCM credentials uploaded to Expo (owner input).

V10 runs on a real Android phone only (DECISIONS R-24).

- [ ] A dead token is cleaned up.

### Findings

- **D1 (defect, low): a NUL character in a token, `deviceId` or `deviceLabel` answers 500.** `POST /push-tokens {"expoPushToken":"ExponentPushToken[ab\u0000c]","platform":"ios"}` passes `EXPO_TOKEN_PATTERN` (`[^\]\s]` admits U+0000) and Postgres refuses it (`22021 invalid byte sequence`), so the person sees "Something went wrong" instead of a 400; same for `deviceId` `"a\u0000b"`. The hub log holds Prisma's error text, not the token. Expected: a 400 like every other malformed token.
- **D2 (defect, low): `push-token.contract.spec.ts` leaves `wawu_hub_test` as it did not find it.** The spec deletes the seeded follow from the plain user to the basic creator (lines 359 to 379) and never restores it: run alone, `FollowRelationship` goes from 2 to 1 (README "Test hygiene rules": a spec must leave the database exactly as it found it). After the whole suite main ends with 0 there too, so nothing else fails today.
- **D3 (defect, low): invented figures without a marker.** `PUSH_BATCH_LIMIT` (500 per tick), `PUSH_REQUEST_TIMEOUT_MS` (20 s) and the hourly prune interval are numbers the builder chose; the PUSH-TIMING marker's own words cover only "the sweep, the look-back, the retries, the receipt checks and the lock", and the marker sits on one constant (the other constants of that group, `PUSH_LOOKBACK_MINUTES`, `PUSH_RETRY`, `PUSH_RECEIPTS`, `PUSH_LOCK_SECONDS`, are covered by prose only). The gate reads only the 4 lines that carry `PROVISIONAL(...)`. Add a marker to each of the three, or widen PUSH-TIMING's text.
- **D4 (defect, medium, conditional): the sender mixes two clocks, so it breaks when the database timezone is not UTC.** Times written from Node (`nextAttemptAt` on a retry, `receiptDueAt` for the first receipt check, `sentAt`) are UTC wall-clock values in `timestamp` columns, and they are compared with SQL `now()` (a `timestamptz`, read in the session timezone). With the database timezone set to `America/New_York` (UTC-4), a 503 left the delivery `pending` with `nextAttemptAt` 4 hours in the future (one attempt, no retry in the 30 s watched); a timezone east of UTC makes retries and the first receipt check fire early. The local Postgres here is `Etc/UTC` and nothing in `deploy/` pins the server's timezone, so production's is unknown. One clock (all SQL `now()` plus interval, or all parameters from Node) fixes it.
- **D5 (unclear, low): a 403 from anywhere is read as "Expo refused the push credentials".** Any 401 or 403 is logged "Check EXPO_ACCESS_TOKEN" and the delivery is failed for good (no retry), as happened here when the egress proxy answered 403. A firewall or proxy denial would lose every push in its window and point the operator at the wrong cause. Real Expo's own answer for a bad token is not known (NOT RUN).
- **D6 (unclear, owner or INBOX-21): the message has no `sound`, `priority` or `channelId`.** Expo's defaults then apply (no sound, normal priority, the app's default channel). Nothing assigns the Android channel to a task (INBOX-21's scope does not mention it). Not something Expo would reject.
- **D7 (unclear, low): test gaps** named under Mutants: log and warn leaks are invisible to the log spec; no spec holds a fresh `sending` row against the reaper; no spec covers a timed-out send. The behaviour is right today (checked live above).
- **D8 (unclear, low): "within a minute".** The first receipt check is due 60 s after the send, the sweep runs every 10 s: a notification is sent within about 10 s and recorded `delivered` about 70 s after the send (observed 70 s), up to about 80 s after the notification. Against real Expo this cannot be judged (NOT RUN); the phone side is INBOX-21's "within a minute of a new follower".
- **D9 (unclear, owner): are device tokens part of a person's data export?** They are excluded with a reason (a token is an address that anyone holding the file could use); the entry passes the export-map spec. Whether the person has a right to see which phones are registered is not decided anywhere.
- **D10 (differs-for-recorded-reason, `docs/contract/PUSH.md` section 1): `DELETE` of another person's or a missing token answers `200 {removed:false}`, not 404.** The two cases are indistinguishable, so the route cannot show whose phone a token is; the token is in the body, never the URL.
- **D11 (differs-for-recorded-reason, G-265 and G-266, builder defaults for the owner): held kinds and amounts on a lock screen.** Six kinds are held; `sale`, `tip_received`, `dm_received`, `dm_refunded` carry the amount in the push text. Owner questions, not defects.
- **D12 (unclear, merge order): `wmt/LEGAL-03` adds the notification kind `legal_delivered`.** `PUSH_RULE` is a `Record` over every kind, so after both merge the build fails (TS2741) until a line is added to `push-policy.ts`; git will not report a conflict. Whoever merges second adds `legal_delivered: 'hold'` or `'send'` with its switch. Same for any later kind. No other open branch touches `notification-event.ts`.
