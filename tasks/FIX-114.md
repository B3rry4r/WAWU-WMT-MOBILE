### Which sends are rows (Hub, `inbox-feed.sql.ts`)

- Kind `wawu_user` only (a send to a bank account is not a chat moment), status `pending`, `completed` or `reversed` (a failed send is never a row), and only the sends the person made or received (`payerWawuUserId` or `recipientWawuUserId` is the caller).
- A send still `pending` is its sender's row only: the receiver has nothing yet, so the receiver sees it once it is `completed`. Default (lead), owner may override.
- A `reversed` send stays a row for both people and reads "Reversed ₦X" (the word the wallet history uses). Default (lead), owner may override.
- A send that paid a money request is the request's row, not a second one (`MoneyRequest.transferId` names it): one money moment, one row. Default (lead), owner may override.
- Ranked by when the send was made (`createdAt`), so a row does not move when its status changes. The chat is found from the pair of people (either order), so no chat is created and none is needed in the schema.
- Every figure is the send's own row (`amountKobo`, what the receiver got; fees are not in it). Nothing is added into a total or a balance, and no total is served.
- `canMessage` is false when either person blocked the other (as on a request row); the row still opens the chat.

### Hub change (additive, nothing in the protected registry changes)

No migration, no table, no new route. `GET /inbox` takes one more `kind` value, `money`; `InboxItem.kind` gains `money_move`; `InboxItem` gains an optional `moneyMove` (`transferId`, `chatId`, `direction`, `other`, `amountKobo`, `note`, `status`, `canMessage`), present only on a `money_move` row. `inbox-cursor.ts` accepts the new key `money_move:<id>`. Contract: SHARED-CHANGES FIX-114 #1. Records: `BACKEND_GAPS.md` G-INBOX-15-1 (sends closed) and G-FIX-114-1 (tips and refunds, open).
