# SETTINGS-07 · Notification switches the server honours

## Read first

- `docs/WORKFLOW.md` (the rules every task follows)
- `docs/roles/BUILDER.md` or `docs/roles/VERIFIER.md`, whichever your prompt names

- This task changes `wawu-backend`. Start the session with that repo and `wawu-wmt-mobile` both attached; follow that repo's CLAUDE.md for its commands.

## Goal

Z3's switches work: a user who turns a kind of notification off stops getting it, and nothing else changes.
Split from SETTINGS-03 so each task touches one repo.

## Scope

The notification keys Z3 draws and the server lacks (moneyIn for tips, sales and transfers; communityMessages per
message; contentReviews for approved and sent back), stored with the existing settings and honoured by every
sender, including push (INBOX-03). Additive: existing keys and their behaviour stay.

## Capability checks

- [ ] A user who turns off "New followers" gets no notification when someone follows them, and still gets every other kind.
- [ ] Each of the three new switches is saved, read back, and honoured by the sender of that kind.
- [ ] V3: the web's existing notification settings behave the same.

**Findings**

- **F-1 · communityMessages not stored (judgement asked for). Label: differs-for-recorded-reason for this task, with an unrecorded consequence for SETTINGS-01 that needs the owner (unclear). Severity: medium.** Z3 (rendered, `ev/Z3-light.png`) draws seven switches in four groups: Money in ("Tips, sales, transfers", on), Refunds (on), Paid questions ("Including reply deadlines", on), Community messages (off), Reviews ("Approved or sent back", on), New followers (on), From WAWU ("News and offers", off). A Community messages switch that saves but notifies nobody would promise something the system does not do; CLAUDE.md rule 7 and WORKFLOW section 7 count a claim about what notifications the system sends as a fact the design does not decide. So leaving the key out is the honest choice, and WORKFLOW section 10 allows exactly this: a sensible default decided and recorded as "Default (agent), owner may override" (item 2 of the builder's defaults, and G-19 names what unblocks it). It is not a defect against the backend, and the capability check as written ("honoured by the sender of that kind") cannot pass for a kind that has no sender. What is missing is the downstream record: `SETTINGS-01` still says "Never change the screen to fit the API" and checks "a user can toggle each category" with `depends_on` SETTINGS-07, and `docs/designer/BRIEF.md` has no Z3 entry saying the row is not built at launch, so a screen without the row would fail V5 against the artboard and one with an acting row would send a key the server answers 400 for (`communityMessages` is refused by the whitelist, verified). My recommendation: the mobile Settings screen draws no Community messages row until a sender exists, recorded in the BRIEF "Not built at launch" and in SETTINGS-01's checks; the server should not store a key with no sender (a stored key would let the screen show a working switch that does nothing); G-19 needs an owner task for the sender ("none yet" leaves rule 8's blocker with no one carrying it). The owner may rule otherwise (store it now so a future sender honours choices made today).
- **F-2 · "Paid questions" does not cover new paid questions. Label: unclear (owner). Severity: medium.** Z3's "Paid questions, including reply deadlines" maps to `dmReminders`, which gates only `dm_deadline`. `dm_received` (a new paid question arrives) is ungated by the builder's default 4 ("no switch on Z3"), but Z3 does have one that reads as covering it. A user who turns it off still gets every new paid question. Gating `dm_received` by `dmReminders` would change what the web's existing key does (the scope says existing keys and their behaviour stay), so this needs a ruling: a new key, or accept and word the row. The default's reasoning is wrong in fact (the switch exists) and should be restated.
- **F-3 · "Reviews: approved" has no sender. Label: differs-for-recorded-reason (G-20; builder default 3). Severity: low, but a copy risk.** Admin approve (`decide(..., 'approved')`) emits nothing at any setting; `content_published` is mapped to `contentReviews` and has no caller. The Z3 subtitle "Approved or sent back" is therefore half untrue today. G-20 gives the approval row no owning task ("none yet"), and the mobile screen needs to be told to word it "Sent back" until one exists (the same question as F-1). Likewise the "transfers" in "Money in: Tips, sales, transfers": no transfer notification exists, and WALLET-10 will add it.
- **F-4 · Later kinds are ungated unless someone adds them. Label: unclear. Severity: low.** The gate is a map by kind (`SETTINGS_GATE`); a kind not in the map is never muted. G-20 says transfers and approvals "go through `emit()`, so the switches already cover them". That is true for `content_published` only: a new transfer kind (WALLET-10) and any new community kind need their own map entry or they ignore Money in and Community messages. WALLET-10's text ("With Money in turned off, no notification is sent") does not say it must add the entry, and no test fails when a kind is added to the vocabulary without a decision. Suggest the entry in WALLET-10's scope and a test that every `NotificationKind` is either in the map or on an explicit ungated list. G-21 (push must send only for a row `emit()` returned) is the right rule, with one gap: `emitCampaign` returns a count, not the rows or recipients, so a campaign push cannot follow "the row emit() returned" without changing it; and push must fire after any caller's transaction commits.
- **F-5 · `null` for a new key clears it; the same for an old key is a 500. Label: unclear. Severity: low.** `PATCH {"moneyIn": null}` answers 200 and returns the row to NULL (key absent again) because `@IsOptional()` lets null through and the column is nullable. The contract says boolean only. For the six old keys `null` is a 500 on main and on the branch, byte-identical, so no regression. It is harmless (NULL means on), but it is unspecified; a client could rely on it as "reset", or the DTO could refuse null like the others.
- **F-6 · Contract says `boolean | null` for keys the server never sends as null. Label: unclear. Severity: low.** The generated client types `moneyIn?: boolean | null`. Harmless, but the SETTINGS-01 builder must handle `null` that cannot occur; marking the property non-nullable in the wire schema would give `moneyIn?: boolean`.
- **F-7 · The new spec leaks rows into `wawu_hub_test`. Label: defect. Severity: low (test hygiene, no live effect).** README "Test hygiene rules": a spec must leave the database as it found it. After one full contract run the branch leaves 13 completed tip Purchase rows against 4 on main (the spec deletes its content purchase but not the tips it creates, 9 per run); it grows on every run. Not a user-visible defect and not a merge risk for the live server.
