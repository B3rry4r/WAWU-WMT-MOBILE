## Goal

Money that arrives or settles while nobody is looking is still recorded once.

## Scope

Webhook endpoint with signature check, an event store keyed by the transaction reference (Fintava sends no event id), safe to replay.

There is no standing tunnel (R-25): locally, webhook checks send payloads built from Fintava's documented format (`docs/fintava/reference/`) and signed with the local secret to the local endpoint, and the report says so. Real payloads are recorded into `docs/fintava/sandbox/23-webhooks.md` once OPS-10 registers the production webhook URL, or when Fintava sends samples (unblocking fact). The production webhook URL is registered by OPS-10.

## Fintava facts

From `docs/fintava/naira-api.md`; a real sandbox response overrides it.

Signature: HMAC-SHA512 of the raw body with the dashboard webhook secret, hex, in `x-fintava-signature`, compared in constant time. No timestamp and no event id: deduplicate on the transaction reference (with the event name, since a send and its reversal share a reference). Retries until a 200: live every 3 minutes for 4 tries, then hourly for 72 hours; sandbox hourly for 72 hours. Events: `account_funded`, `virtual_wallet_payment` (possibly upper case), `customer_bank_transfer`, `wallet_to_wallet_transfer_v2`, `debit_transfer_reversal` (how a failed bank send shows up), `card_payment`, `dynamic_card_payment` (card payloads unpublished). The name field is `event` in one page and `type` in another: read both. References per event (`reference/webhook-events.md`): `account_funded` carries `reference` and `sessionID` (no reference of ours); `virtual_wallet_payment` our `merchantReference`; `customer_bank_transfer` `reference` and `customerReference`; `wallet_to_wallet_transfer_v2` only `reference`; `debit_transfer_reversal` `customerReference`, `transactionReference` and `reversalRef`. A transfer RESPONSE swaps `reference` and `customerReference` (`sandbox/11-`); whether a delivery does too is unconfirmed until a real one is recorded (BACKEND_GAPS G-19).

**Findings**

1. `defect` (money). `@SkipThrottle()` on `FintavaWebhookController` (`src/fintava/webhook/fintava-webhook.controller.ts:36`) does not take the webhook out of the global `ThrottlerGuard`. `AppModule` names its throttlers `short` (20 per second) and `medium` (200 per minute) (`src/app.module.ts:86-89`); `SkipThrottle()` defaults to `{ default: true }`, which skips only a throttler called `default`. On the production build of `9941aa0`, 30 different, correctly signed deliveries sent together got 20 times 200 and 10 times 429 "ThrottlerException: Too Many Requests", and only 20 rows were stored. The same build with only that decorator changed to `SkipThrottle({ short: true, medium: true })` (a diagnostic copy, not a change to the branch) got 30 times 200 and 30 rows. The 429 is never logged, so a dropped delivery is invisible, and Fintava resends it only 3 minutes later and then hourly. The controller's comment ("Throttling is skipped") and status-code list (200/400/401/503) both say otherwise, and the spec builds its app without AppModule's guard, so removing the decorator entirely still passes 35/35. Behind nginx, `main.ts` sets no `trust proxy`, so every caller probably shares one tracker and Fintava competes with all API traffic for the 200 a minute (read from `deploy/provision.sh` and `main.ts`, not checked on the droplet). Unblocked when the webhook skips both named throttlers (or every throttler) and a test sends more than 20 signed deliveries a second through an app that has the real global guard. The Flutterwave webhook on main has the same gap (`src/payment-webhook/payment-webhook.controller.ts:31`); that is outside this task and is left for the owner.
2. `defect` (money, unlikely input). A correctly signed delivery whose JSON has `\u0000` in any string can never be recorded: Postgres `jsonb` refuses it (Prisma `P2039`), the endpoint answers 503, and every one of Fintava's retries over 72 hours fails the same way, so the delivery is lost. Reproduced on the production build: 503, log line `fintava webhook account_funded: not stored (PrismaClientKnownRequestError P2039)`. `rawBody` is `TEXT` and would take it; only `payload` refuses. Sender names and narrations come from other banks, so the content is not fully Fintava's. Unblocked when such a body is still stored once (for example `payload` without the NUL escapes, with `rawBody` kept exact) and a test sends one.

Notes, not defects:
- A body with invalid UTF-8 is accepted and keyed correctly, but `rawBody` holds U+FFFD in place of the bad bytes, so it is not byte for byte. JSON on the wire is UTF-8 (RFC 8259), so Fintava should never send one.
- A delivery that is not `application/json` (or form) is refused with 400 on every retry. The docs' own sample uses `express.json()`; confirm the content type when OPS-10 records the first real delivery (G-19).
- The builder's file list matches `git diff --stat` on both repos; `docs/LOG.md` and the generated `docs/PROGRESS.md` are also in the mobile diff. No stand-in for anything main has: main's only webhook store, `PaymentWebhookReceipt`, is Flutterwave's settlement claim, and the signature guard is new because Fintava signs differently.
- The builder's contract run had 40 failures; on a fresh database with the mock on :4001 there are none, so they were the :4001 suites, as the report says.
