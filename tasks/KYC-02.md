**Defects**
1. `defect` (identity, blocking): **a 2xx that does not say "match" opens the door.** `readSelfieResult` (`src/fintava/fintava-client.ts`) answers `matched: !verdicts.includes(false)`, so any 2xx `data` object without a boolean `false` under one of seven names is a match: 11 shapes in the table above, including the documented `{}`, `status: "failed"`, `match: "false"` and `confidence: 0`. MONEY-12 would then open an account on it. Fix: `matched` is true only when a verdict field is literally `true` (and nothing in the body says the check failed); every other 2xx is not a match, is counted (it was charged) and does not set `matchedAt` (a 503, or a code of its own). Until Fintava shows the success body (question 6), no selfie passes, which is the correct state. The builder's tests assert the opposite and change with it (`SELFIE_200` passing, "Fintava’s documented 2xx (no score) passes", and the client spec's "a 2xx with a data object is a match").
2. `defect` (identity, blocking): **a selfie matched against one BVN can count for another.** `match()` compares the BVN (`matchesCheckedIdentity`), then inserts the attempt row; `matchedAt()` later accepts any matched row created after the current `bvnVerifiedAt`. If a BVN check for BVN B passes between that comparison and the insert, the selfie is sent and matched against BVN A's photo but counts for B. Shown deterministically (a hook runs B's check right after the comparison: route 200, Fintava saw BVN A, current BVN B, `selfieMatched` true) and **without any hook**: B's check and A's selfie fired together for one person, 2 of 40 and 2 of 100 trials ended with `selfieMatched` true for B. That is the SIM-swap case the selfie exists for (B's check needs B's phone on the account). Fix: bind each attempt to the check it was compared against, read once (for example store that check's `bvnVerifiedAt`, or the BVN hash, on `SelfieMatchAttempt` from the same `WalletIdentity` read as the comparison; the table is new in this unmerged migration), and have `matchedAt`/`selfieMatched` require it to equal the current check.
3. `defect` (low; cost and contract): **polyglot images pass the JPEG/PNG check.** `isSelfieImage` checks only the first 3 or 8 bytes, so JPEG or PNG magic followed by anything (HTML, a ZIP, random bytes) is accepted and would be sent and charged. It does not raise the cost bound (3 a day per person still holds, and a real non-matching photo costs the same), so it is low; but the route promises a JPEG or PNG and "the app checks the photo before sending it" (`naira-api.md`). Fix: also require the format's end (JPEG ends `FF D9`; PNG has `IHDR` at byte 12 and ends with the `IEND` chunk), or read the dimensions.

**Findings (not defects)**
1. Echo masking holds for Fintava's real format (standard base64 inside a JSON string, fully replaced by `[data]`). Echoes in other encodings would leave fragments under the 200-character cap: 24-character windows of the image found in the log for a base64url echo (124), a `\/`-escaped echo (21) and a 30-column wrapped echo (42); a JSON-in-a-string echo 0. None is a selfie (at most about 150 bytes of a JPEG header). The two surviving mutants (threshold 40 -> 400, cap 200 -> 2000) show the tests do not pin either; worth a test each.
2. `matchesCheckedIdentity(..., nin: string | null)` no longer makes a caller pass a NIN: a later `dto.nin ?? null` would compile and skip it. Today the selfie is the only caller and is right to pass `null`. A separate `matchesCheckedBvn(user, bvn)` would keep the NIN required for MONEY-12. MONEY-12's verifier should check its call passes the NIN.
3. A client-side refusal (`FintavaClient.refuse`, kind `validation`, nothing sent) would be counted and answered as A16; unreachable today because the DTO is stricter than the client.
4. The per-address throttle runs before validation and auth, so a 400 or 401 uses one of an address's 3 a minute (seen on the production boot); pre-existing guard order, same as the BVN route. KYC-03's screen should validate the capture locally.
5. Mobile: `matchSelfie` resolves on any 200 even if `matchedAt` were null; the server never answers that today, but KYC-03 should read `matchedAt`, not the resolve, as A7.
