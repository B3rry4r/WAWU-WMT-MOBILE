**Money and identity safety notes**
- WAWU keeps no copy of any file; Nuvion is the only holder. Kept: kind, sides, state, Nuvion's document id (and every id the row has recorded), the time, a SHA-256 of the bytes so the same file is forwarded once. The ID number is not here at all (NUV-02 sends it with the entity and stores nothing). Logs name the operation, status and request id, never a body.
- A document is `uploaded` only when Nuvion's answer names it. An unknown outcome (a timeout, a 5xx, an unreadable 2xx) leaves `unknown`; nothing is sent again until the call's own time has passed and Nuvion's own list of the entity's documents has been read, and a document already on file (any id the row ever recorded, or another row's) is never taken for a lost upload. A list that cannot be read sends nothing.
- The submission is behind a claim taken by a conditional update before anything is sent; a lost answer is looked for (the entity past `incomplete`, `pending` or approved) before it is sent again; Nuvion's `error_entity_status_not_incomplete` is read as "it has it" only when the entity is in review, never when it still shows an earlier `rejected` (mutant M28).
- A disagreement between Nuvion and our record is a stop: an entity id another row names, or a document id another row holds, is never adopted; a submission Nuvion refused is not hidden (the claim goes, the person sees `submitted: false`).
- No amount, fee, price, limit or currency is handled here. The per-person upload limits and the uploads at once are `PROVISIONAL(NUVION-DOCUMENT-UPLOAD-LIMITS)` with a reason; the 30-minute session window and the one-hour refusal memo are `PROVISIONAL(NUVION-LIVENESS-WINDOW)` and `PROVISIONAL(NUVION-LIVENESS-MEMO)`. nginx's `client_max_body_size 25m` (deploy/install-services.sh) holds two 10 MB files.

**Decisions** (Default (agent), owner may override)
- **The two sides of an ID go in one request** (`file`, `file_back`); the brief's `side` field is not a request field (`side=front` is accepted, `side=back` is refused). Nuvion's call takes both sides together, WAWU keeps no copy to hold a front until a back arrives, and a lone back would be taken for a front. The screens hold the front image until the back is captured (G-470).
- **The hosted selfie is OFF by default** (`NUVION_HOSTED_LIVENESS`, empty is off) and drops itself for an hour when Nuvion refuses to start one. Reasons: the API is only in Nuvion's dashboard code and unproven for child entities (the (key) check settles it), Nuvion's own quickstart approves an individual without it, and the screens that carry a person to the hosted page and back are not built, so a required step with no screen would stop every opening and nobody would be approved. The code for it is built and proved with it on. Flip it to `on` (and set `NUVION_LIVENESS_REDIRECT_ORIGINS`) only after the (key) check and the hand-off screens (G-471).
- **A document or a submission whose answer was lost waits the call's own time plus 15 seconds, not the money timeout plus ten minutes**, before Nuvion's list is read and, only if the document is not there, it is sent again: a second document costs nothing (Nuvion holds one more) and a second submission is refused by Nuvion as "not incomplete", which is read as "it has it". The list is read before anything is resent in every case.
- **A submission Nuvion refused is not sent again for a minute**, or until a document changes; a transient failure of an upload reads `missing` (send it again), only a refusal reads `not_accepted`.
- **Documents are taken only while the opening is at `needs_documents`**: after a refusal the person first sends the corrected details (`POST /money/wallet/open`, NUV-02), then the documents; a document-only refusal still needs that first step until Nuvion's behaviour on a `rejected` entity is known (G-473).
- **`GET /money/identity/documents` and `/liveness` can send the submission when it is due** (a correction, a webhook that never came, a lost answer): the claim makes it safe to call from anywhere any number of times.
- **The routes' own `reason.code` set** (`document_request_invalid`, `document_file_invalid`, `document_not_accepted`, `documents_closed`, `document_in_progress`, `document_rate_limited`, `document_busy`, `selfie_not_available`) lives in `src/nuvion/documents/document-errors.ts` with its own contract envelope, not in the money contract's shared lists, so no other task's edit of those lists meets it; it answers the same envelope shape and the four codes the money contract already has (`wallet_not_open`, `identity_under_review`, `provider_unreachable`, `not_found`).
- The file check reads the type from the first bytes (PDF with an end marker, JPEG, PNG signature) and does not walk the picture: an ID photo can be far larger than a selfie, and Nuvion judges the content (its refusal comes back as `document_not_accepted`).
- Any refusal of a session start that is not a lost answer (auth, refused, not supported, not found, validation, identity refused, wallet inactive) is read as "Nuvion will not start one for this person": the opening goes on without a selfie.
- Per-person upload limits (8 in 10 minutes, 30 a day), 4 uploads in memory at once (5 s wait), 6 sessions an hour: `PROVISIONAL(NUVION-DOCUMENT-UPLOAD-LIMITS)`.

**The decisions, judged**

2. The hosted selfie off by default: agree (unproven for child entities, no screens). Its self-switching-off is D2.

4. A refused submission is not sent again for a minute: agree for the loop guard; the person is told nothing (U3).
5. Documents only at `needs_documents`, details first after a refusal: agree as a rule; the implementation fails for a refused document (D1).
6. `GET` sends the submission when due: agree (the claim makes it safe: O6 to O9, H5), and the screens should treat these reads as having an effect.
7. The routes' own `reason.code` set: agree; every refusal I made carried one, and the contract lists them per route.
8. The type read from the first bytes, framing only: agree, with U5.
9. Any refusal of a session start means "no selfie for this person": disagree (D2).
10. The limits (8 in 10 minutes, 30 a day, 4 at once, 6 sessions an hour) as `PROVISIONAL`: agree; see U6 and U7.
11. **The SHA-256 of the bytes kept per document.** Needed: it is what makes the same file go once (double tap, retry after a lost answer, two servers) and the live runs depend on it (O1 to O3, O10c). Not safe as built: an unkeyed SHA-256 lets anyone who can read the table test whether a person uploaded a given file, and links accounts that upload the same file (it is also the format of Nuvion's `content_hash`). The BVN already gets a keyed hash (`IDENTITY_HASH_KEY`); the fingerprint should be an HMAC with that key, and could be cleared once the opening is sent (after that only "the same file again is the same answer" uses it). Low; not a defect against the brief, which asked me to judge.
12. WAWU keeps no copy of any file: agree and verified (V4).
13. The edits to NUV-01's files (SHARED-CHANGES NUV-03 #3): additive and safe.
