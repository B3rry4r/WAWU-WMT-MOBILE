## Findings

1. **medium** `POST /uploads/confirm` answers 500 "Something went wrong" whenever it waits more than 5 s for the person's storage lock. The confirm transaction (`src/storage/storage.service.ts:764`, `adoptArrived`) takes the lock but not `LOCKED_TX`, so Prisma's 5 s default applies, while a release (`upload-release.ts:84-125`) or a sweep removal (`late-file-sweep.ts:295-349`) holds that lock across the bucket DELETE. Repro: `scripts/k1.py 12` (DELETE 12 s: confirm 500 after 9.0 s; create 201 after 9.0 s), `scripts/k4.py` (sweep with a 12 s DELETE: confirm 500 after 10.0 s, create 201). Hub log: "Transaction API error ... timeout 5000 ms, 8969 ms passed". The brief's own test (a slow bucket must not make confirm fail) fails at a 5 s DELETE. Fix: `LOCKED_TX` on confirm, and bound the DELETE (see 2).
2. **medium** One person's burst of releases starves the Hub's connection pool for everyone. Release, create, PATCH, confirm and each sweep row hold a pooled connection while they wait for the person's advisory lock, and the holder keeps its connection across the DELETE; the S3 client has no request timeout (`storage.service.ts:390`); the cron has no overlap guard (4 connections per run). `scripts/p1.py 20 3` (20 concurrent releases by one person, DELETE 3 s, the route's limit is 20): 6 of 20 releases 500 ("Unable to start a transaction in the given time", `maxWait` 15 s), and another person's `GET /users/me` stalled 14.6 s (max latency; reproduced twice). With a 0.15 s DELETE the other person still stalled 1.3 s. Round 3's release held no connection during the DELETE, so this is new in round 4. Fix options: a request timeout on the S3 client (a few seconds); do the DELETE outside the transaction (mark under the lock, delete, finish under the lock); or `pg_try_advisory_xact_lock` and answer 409/503 instead of queuing.
3. **low** The stated limit is wrong: create/PATCH/draft publish "wait up to 15 s for the lock" (builder item 4). `maxWait` 15 s only covers getting a connection; the lock wait runs to the 60 s transaction timeout: create waited 22 s of a 25 s DELETE (201) and 57 s of a 70 s one (201); with four queued 20 s releases the later releases failed at 60 s and the create only passed because it was served third (`k1.py 25|70`, `k3.py`). Also, when the DELETE outlives the 60 s transaction (`k2.py`, 70 s), the lock drops while the DELETE is still in flight: a create naming that key passed (201), then the DELETE removed the file: a live piece with a missing preview, row `pending` (counted), and the release answered 500 "Something went wrong" instead of the 503 text. Own key only.
4. **low** Photo-set frames are claims (`isClaimed` reads `ContentFrame`) but `PUT /content/:id/media` (`content-media.service.ts` `ownedFrameKeys`, ~174-199) checks the row outside any lock or transaction. Release racing a frame set (`m1.py`, 40 rounds): 39 of 40 both answered 200 and ended with a frame on an `abandoned`+released row with no object (a dangling frame). Not a quota bypass (a late PUT of that file is claimed, so the sweep counts it). Fix: take `lockStorageQuota` and re-check inside the frame transaction, as create does.
5. **low** An honest slow upload (more than 15 min, any usage read in the middle abandons the pending row) that then lands is refused by create: 400 "One of these files was released or never arrived. Upload it again." (`scripts` inline test; the file is in the bucket). It recovers through `POST /uploads/confirm` (the ME-04 app never calls it) or when the sweep counts the file (within 10 min). Round 3's finding 3 changed shape (was: the sweep deleted it).
