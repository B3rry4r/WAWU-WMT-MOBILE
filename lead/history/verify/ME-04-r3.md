## Findings

1. **medium** A released file that lands late and is then named by a listing stays uncounted and is never removed: the quota bypass of round 2 survives, through the lead's own rule "a claimed key is never deleted". Cycle: presign preview and full, PUT, `POST /uploads/release` both (200), PUT both again with the same links, `POST /content` naming the two files (201: `content-piece.service.ts` create never reads the `StorageObject` row), then `DELETE /content/:id` (204, the slot is free again, slotsUsed 0; a removed piece still counts as a claim in `isClaimed`). The rows stay `abandoned` + `releasedAt`, so `usedBytes` leaves them out; the sweep finds them claimed and only sets `sweptAt` (`late-file-sweep.ts` settleOne, "isClaimed" branch). Result after 5 cycles and a sweep past the margin: usedBytes 0, bucket 41,943,040 bytes in 10 objects, rows `abandoned swept=true removed=false` x10. Each cycle is inside the 200/min limit, so no ceiling. The same cycle with a live piece (not deleted) also stays uncounted. Photo sets are safe (`content-media.service.ts:182` refuses an `abandoned` row); `POST /content` and its PATCH (`content-piece.service.ts:630, :798`) do not.
   Repro: `scratchpad/me-04-v/r3/scripts/f1.py` (log `logs/f1.log`), and `e2.py`/`e3.py` for the live-piece form.
   Fix options: `POST /content` and PATCH refuse a key whose row is `abandoned`/released (as photo-set frames already do); and/or the sweep, on a claimed `abandoned` row, counts it again (set `confirmed`) instead of only marking `sweptAt`.
2. **low** release racing `POST /uploads/confirm` leaves a counted phantom the person cannot clear. `adoptArrived` (storage.service.ts, the `tx.storageObject.update` by id) is unguarded and `releaseOwnUpload` takes no lock, so when the release's update lands first the confirm then sets the row `confirmed` with `releasedAt` set, and the object is already deleted. A second release is a no-op (`updateMany where releasedAt: null`), so the space stays counted for good. Rate on an idle machine: 15 of 45 rounds (pending row, file present) and 27 of 50 rounds (the re-adopt step: abandoned row, file present). Self-harm only; ME-04's app never calls confirm, so only FIX-15's flow reaches it. Fix: guard the adopt update on `releasedAt: null` (or `updateMany`), and make release also fix a `confirmed` row. `scripts/c1.py`, `c2.py`.
3. **low** the sweep deletes a file the person never released: an honest upload that takes longer than 15 minutes, where any usage read (presign, allowance) abandons the still-pending row, then lands. The next sweep (within 10 min) removes it and confirm answers `abandoned`; before this round FIX-15's confirm would have adopted it ("a slow upload that outlived the give-up"). Repro `scripts/l1.py`: row abandoned, PUT lands, sweep removed=1, confirm `abandoned`, used unchanged. Needs a 15 minute upload (512 MB is the format cap) plus a second request in that time, so rare; scope the sweep to `releasedAt IS NOT NULL` if the ruling is "released objects" only.
4. **low** (SWEEP-APP R3-1, numbers) create vs the sweep is not atomic: with a 3 s DELETE, a piece created 1.5 s into the sweep got 201 and both of its files were then deleted (`scripts/g1.py`). Own key only.
5. **low** two sweeps at once both count a removal for the same file (removed 5 and 4 for 6 rows; `settleOne` returns `removed` without reading the `updateMany` count). Cosmetic: the delete is idempotent and the third pass sends nothing.

## The builder's R3-2 and R3-3

- R3-2 (a person keeps counted space by walking away from a draft): **low**. Only their own quota is held; it is counted, not hidden; no one else is affected; it is a ruling.
- R3-3 (a very slow PUT past the margin lands uncounted): **low, but close to medium**. The sweep looks at a row once (`sweptAt`); a file that lands after it stays uncounted forever (`f1.py`: swept while the PUT runs, file lands, second sweep does nothing, used 0). Abuse needs a PUT that stays open at least 10 minutes past the link's life and a bucket that tolerates it (not testable here: no real storage). Cheap to close in the same fix round: look at a swept row a second time later (for example after an hour).
