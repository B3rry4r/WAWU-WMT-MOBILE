## Findings (all low or notes)

1. **low** The app drops a refused give-back: `src/features/create/draft.ts:45` sends `releaseUpload(...)` fire-and-forget and swallows every error, so a 429 `storage_busy` (like the old 503) leaves that file counted until a later release. Not reachable by a normal flow: the app releases at most 2 files per action (full + preview), calls no other capped route (only presign and release; `/uploads/confirm`, `POST /content`, PATCH, PUT media and publish are not called by the app yet), and the turn is held only for the short database step. It needs 4 releases of one person inside one transaction time (about 4 taps in under 50 ms). ME-08 should retry a refused release after `Retry-After`.
2. **low** Requests that do not need the database lock still take the person's turn and can be refused: a text-only PATCH (`content-piece.service.ts:983`, `assertFilesNotGivenUp` returns before locking when no file is named) and a PUT media with only `pageCount` or `durationLabel` (`content-media.service.ts:268`, the lock is taken only for `frames`). With the lock held from outside, a media burst admitted 4 (not 3) because the pageCount-only ones finish at once. Harmless; the cap is just broader than it needs to be.
3. **low** (note for the merge) A new 429 `storage_busy` is possible on `POST /content`, a protected route the web calls, but only for a 4th simultaneous request of one person on one Hub process (the route already answers the throttler's 429). The contract lists no 429 (nor 400, 409, 413, 503) for these routes, so nothing is out of line with the contract. CI "Protected route suite" is green.
4. **note** `reconcileStale(wawuId)` runs before the turn in confirm, so a refused confirm may still have settled other stale `pending` rows (housekeeping any allowance read does). The row the request named is untouched. Across two Hub processes the cap is per process (2 x (1 running + 2 waiting) per person), as the brief says.

Closed from round 5: finding 1 (medium); finding 2 (migration order) is now in the task file's merge order and the builder noted it; finding 3 is sweep row R5-3 by decision.
