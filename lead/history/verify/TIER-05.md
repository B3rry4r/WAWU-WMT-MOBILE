## Findings
1. HIGH. Starvation: the sweep reads only the 64 OLDEST waiting orders and filters "due" afterwards, so with 64 or more unfunded orders waiting, a newer order whose money has landed is never looked at until older ones expire (up to 24 h). src/plans/purchases/plan-transfer.service.ts sweep(): `findMany({ where: { status: awaiting, expiresAt: { gt: now } }, orderBy: { createdAt: 'asc' }, take: TRANSFER_DEFAULTS.batch })` then settlePerson skips what is not due. Also an abuse path: a few accounts with open wallets can park 64 orders (several tiers x bump each) and stop every other transfer purchase completing. Repro: v-tier05-fintava.contract.spec.ts D1 (70 unfunded orders, then one funded: sweep reports paid 0, order stays awaiting, 0 sends). Fix: select due orders (nextCheckAt <= now, or people with a credit newer than creditsSeenAt), or page through all waiting orders; keep the batch only as a page size.
2. LOW (rare, false message on a money path). If the payment is made and the process fails before the order is linked (order goes back to awaiting with backoff 1 to 16 min), and the window lapses before the retry, expireLapsed marks it expired: view says "Nothing was taken from your wallet" while the money was taken and the tier granted. plan-transfer.service.ts expireLapsed() does not look at the order's `transfer-<id>` key. Repro: spec F1 (link fails once, expiresAt set past, sweep: order expired, 1 send). Fix: expireLapsed skips (or first links) an order whose settle key names a payment.
3. LOW. The settlement key `transfer-<orderId>` lives in the person's own Idempotency-Key space (same route 'POST plans/purchases'). A person who sends a wallet purchase of ANOTHER item with that key makes the sweep link the transfer order to that other payment: order reads settled/paid though its own item was never bought (self-inflicted, no money lost, nothing wrongly granted). Also pre-claiming the key blocks their own order. Repro: spec A4. Fix: a key prefix a client cannot send, or check the linked payment's kind and target equal the order's.
4. LOW. A provider refusal of the send that is not in the "released" list (spec B2: unclassified 400 after the balance read) ends the order `settled` linked to a FAILED payment; the view says failed ("No money left your wallet"), the sweep never retries, the person must start again. Same end state as a failed wallet payment, but the transfer order is the one place that money has already landed. Consider waiting again for a refusal that moved nothing.
5. LOW (note). Contract: POST /plans/purchases 201 and GET /plans/purchases/{id} 200 change from $ref PlanPurchaseView to oneOf [PlanPurchaseView, PlanTransferOrderView], and PlanPurchaseView.method widens to wallet|transfer. No removals, no path in the protected registry; wallet answers are unchanged. No mobile code calls the route yet.
